# 1단계(0.1.0) 스펙

1단계 구현의 기준 문서다. 흩어진 결정(GLOSSARY, ADR 0001~0008, research 0001·0002·0006, 티켓 0001~0003, 2026-11-17 운영자 결정 Q39~Q61, 같은 날 코디네이터 답 Q62~Q65, 같은 날 운영자 결정 Q66~Q68과 Q63 개정, 그 결정을 구체화하며 운영자가 확인한 코디네이터 답 Q69~Q76)을 한곳에 묶는다. Q39~Q61과 Q66~Q76은 이 문서에 처음 기록하는 결정이고, 본문의 해당 문장이 그 결정이다(Q39·Q49~Q51·Q54·Q66·Q67·Q69~Q71·Q75는 ADR 0004에, Q57은 ADR 0001에, Q63 개정·Q68·Q72·Q73은 ADR 0006에도 적었다). Q49~Q61은 이 문서 첫판의 열린 질문 1~14에 대한 답이고, Q62~Q65는 티켓으로 쪼개며 나온 질문에 대한 코디네이터 답이다. Q66~Q68은 Q62~Q65 중 일부를 뒤집은 운영자 결정이고(Q62는 Q66으로, Q63은 엄격한 FIFO로, Q64는 Q67로 대체했다), Q69~Q76은 그것을 문서에 옮기며 나온 질문에 운영자가 코디네이터를 거쳐 답한 것이다. 이 문서는 새 결정을 만들지 않는다. 근거 문서에 없는 것은 「열린 질문」에 남긴다. 이 문서를 쪼갠 티켓은 `docs/tickets/0004`부터다.

용어는 [GLOSSARY](../../GLOSSARY.md)를 따른다.

## 1. 목표와 완료 기준

목표: 트래커의 티켓을 러너에 맡기고, 런의 결과를 두 축으로 기록해 화면과 통계로 보여 주는 셀프호스팅 제품의 첫 릴리스를 낸다(ADR [0005](../adr/0005-self-hosted-product.md)).

완료 기준(Q48):

- 테스트용 Linear 워크스페이스의 티켓 하나에 Auto-assign Label을 붙이는 것만으로 러너에서 처리된다.
- 그 런의 에이전트 결과와 PR 상태가 기록되고, 두 축에서 계산한 요약 결과(Merged / Human Check / Failed)와 함께 화면과 통계에 나타난다.
- 위를 npm CLI로 설치한 오케스트레이터로 해낸다. 그러면 0.1.0으로 릴리스한다.

## 2. 범위와 제외

범위:

- 온보딩, Tracker Connection(Linear), GitHub 토큰, Runner(Orca over ssh) 등록, Workspace, Mapping, Auto-assign Label
- 수동·자동 할당, 엄격한 FIFO 대기열, 런 시작·감시·연결 끊김 처리·종료, 결과 기록과 요약 계산, Linear 갱신, 워크트리 정리
- 화면: 홈, Tickets, Runs, Run 상세, Runners, Stats, Settings, 온보딩(티켓 [0002](../tickets/0002-html-prototype.md), 시안 B, ADR [0007](../adr/0007-ui-list-detail-panel.md))
- npm 패키지와 CLI(`init`, `start`, launchd·systemd 등록), 업데이트 시 DB 마이그레이션 자동 실행(ADR 0005)

제외(Q47): 다중 사용자, Docker 배포, Linear 외 트래커, Orca 외 러너, 토큰·비용 통계, 자동 재시도, Workspace별 우선순위, 모바일 레이아웃, 라이트 모드.

## 3. 사용자 흐름

1. **온보딩.** 첫 진입 즉시 사이드바 없는 전체 화면으로 뜬다. 트래커 연결 → GitHub 토큰 → 첫 러너 등록과 ssh 확인 → 첫 Workspace(트래커 프로젝트 고르기) → 첫 Mapping 순서이고, 모든 단계가 필수이며 확인이 성공해야 다음으로 간다(ADR 0005·0007). 러너 등록 단계는 9절의 러너 필수 조건을 확인한다. Orca 상시 서비스가 없으면 설치 명령(`orca serve service install`)을 안내하고, 비대화형 ssh 세션에서 GitHub 인증이 동작하지 않으면 그것을 알린다. orca 실행 파일 경로는 러너 설정으로 받는다(Q43, research [0002](../research/0002-external-contracts.md) A.3·A.8). Mapping 단계는 에이전트가 PR 제목에 티켓 키를 넣도록 각 프로젝트의 에이전트 지침에 적기를 권한다(7번, research [0006](../research/0006-github-contract.md) 17절).
2. **할당.** 운영자가 Tickets 화면에서 직접 하거나(수동), 티켓에 Auto-assign Label이 붙으면 오케스트레이터가 한다(자동). 자동 할당은 Linear webhook으로 감지하고, 놓친 이벤트는 주기적 폴링으로 맞춘다(ADR [0001](../adr/0001-tracker-is-source-of-truth.md)). 할당 조건은 "`data.labelIds`에 Auto-assign Label이 있고, 그 티켓에 진행 중이거나 Queued인 런이 없다"로 잡는다(research 0002 B.2, Q45). 여기서 진행 중은 Running, Waiting for Input, Disconnected다(4.1, Q74).
   - **러너 고르기.** Mapping은 러너 쪽 프로젝트와 에이전트만 고르고 러너는 고르지 않는다. 할당 때 그 러너 쪽 프로젝트가 있는 러너 중 Online이고 남은 capacity가 가장 많은 러너를 자동으로 고른다(Q53). 그런 러너가 없으면(모두 Offline) 러너를 정하지 않은 채 Queued로 두고, 그 러너 쪽 프로젝트가 있는 러너가 Online이 되면 같은 규칙으로 고른다. 화면에는 "맞는 러너가 Offline이라 기다리는 중"처럼 이유를 보인다(Q65). 이런 런은 대기열 순서에서 빠진다(3번, Q68).
   - **수동 할당.** Mapping 기본값(러너 쪽 프로젝트, 에이전트)을 채워 보여 주고, 운영자는 러너와 에이전트만 바꿀 수 있다(Q53·Q60).
3. **대기열.** 대기열은 설치 전체에 하나이고 들어온 순서(FIFO)로 엄격하게 꺼낸다(ADR [0006](../adr/0006-workspace-scoping.md)). 맨 앞 런이 시작될 때까지 뒤 런은 같은 러너를 기다리든 다른 러너를 기다리든 모두 기다린다(Q63 개정). 맨 앞 런은 할당 때 정한 러너에 남은 capacity가 생기면 시작한다.
   - **Offline 예외.** 맞는 러너가 모두 Offline이라 러너를 정하지 못한 Queued 런은 엄격한 순서에서 빠져 뒤 런을 막지 않는다. 화면에는 "맞는 러너가 Offline이라 기다리는 중"을 보인다(Q68). 할당 때 러너를 정했는데 그 러너가 Offline이 된 Queued 런도 러너를 비우고 같이 다룬다(Q72). 맞는 Online 러너가 있거나 생기면 2번 규칙으로 러너를 정하고, 원래 들어온 자리로 엄격한 순서에 다시 들어간다(Q73).
   - Linear 티켓은 런이 실제로 시작될 때 "In Progress"가 된다(8번). Queued인 동안은 바꾸지 않는다.
4. **런 시작.** worker가 ssh로 러너에 `orca worktree create`를 보내 워크트리를 만들고 에이전트를 띄운다. 오케스트레이터가 브랜치 이름을 정하고(예: `factory/<티켓 키>-<런 번호>`, Q40), 에이전트는 항상 `--surface terminal`로 띄운다(Q42). 에이전트에게는 티켓만 지시로 준다(GLOSSARY Agent, ADR [0004](../adr/0004-agent-merges-its-own-pr.md)).
5. **런 진행.** worker가 러너를 폴링해 진행을 본다(ADR [0002](../adr/0002-start-web-plus-worker-daemon.md), research 0002 A.6 `orca worktree ps`). 운영자가 Run 상세를 열면 그때 로그 꼬리를 가져와 보여 주고 저장하지 않는다(Q46). 로그 꼬리는 web이 DB에 요청을 남기면 worker가 ssh로 가져와 결과를 DB에 쓴다. web은 ssh를 쓰지 않는다(Q61). 이 결과는 화면에 보이려는 임시 값이라 런 이력으로 남기지 않고 다음 요청 때 덮어쓴다(Q46·Q61에서 따른 것).
   - **입력 기다림.** 에이전트가 사람 입력을 기다리면(권한 프롬프트 등, research 0002 A.6 `--agent-wait`) 런 상태를 Waiting for Input으로 바꾸고 손댈 일에 올린다. 시간 초과 시계는 계속 흐른다(Q52).
   - **연결 끊김.** 런 중(Running, Waiting for Input) ssh가 5분 동안 계속 실패하면 런 상태를 Disconnected("연결 끊김")로 바꾸고 손댈 일에 올린다. 최종 실패가 아니다. 워크트리는 건드리지 않고, 런은 capacity와 티켓당 동시 런 하나 규칙에 계속 들어간다(Q67·Q74). 5분 안에 다시 닿으면 상태를 바꾸지 않고 이어서 지켜본다(Q50). 최대 실행 시간은 Disconnected 동안에도 흐른다.
   - **다시 연결.** Disconnected 런의 러너에 다시 닿으면 실제 상태를 확인한다. 에이전트가 돌고 있으면 Running으로 돌아가 계속 감시하고(입력을 기다리고 있으면 바로 Waiting for Input으로 돌아간다. 결정의 상태 흐름 "Running ⇄ Waiting for Input ⇄ 연결 끊김"을 따른다), 에이전트가 이미 끝났으면 보통 런처럼 두 축을 기록하고 정리하며(7·9번), 워크트리가 사라졌으면 에이전트 결과 "워크트리 없음"으로 끝낸다(Q67). Running이나 Waiting for Input 중에 워크트리가 사라져도 "워크트리 없음"으로 끝낸다(Q49).
   - **돌아오지 않음.** 최대 실행 시간이 지날 때까지 러너에 다시 닿지 않으면 그때 에이전트 결과 "러너 연결 끊김"으로 끝낸다. 러너에 닿지 않으니 에이전트를 멈추지 못하고, 워크트리는 러너가 돌아온 뒤 사람이 정한다(9번, Q67·Q75).
6. **종료 감지.** 에이전트 프로세스가 끝나면 런이 끝난다(에이전트 결과: 종료 코드 0이면 정상 종료, 아니면 오류 종료). 최대 실행 시간(기본 2시간, Workspace별 설정)을 넘기면 에이전트를 멈추고 끝낸다(에이전트 결과: Running이었으면 시간 초과, Waiting for Input이었으면 입력 기다리다 멈춤, Q39·Q70). Disconnected 동안 넘기면 5번의 "돌아오지 않음"이다.
7. **결과 기록.** 런이 끝날 때 에이전트 결과와 PR 상태 두 축을 따로 기록하고, 화면에도 두 칸을 나란히 보인다. 요약 결과(Merged / Human Check / Failed)는 손댈 일 목록과 통계를 위해 두 축에서 계산만 한다(ADR 0004, 4.2 요약 계산 표, Q66). 런과 PR은 1순위 오케스트레이터가 정한 브랜치의 PR, 없으면 PR 제목·본문의 티켓 키로 잇고, 둘 다 없으면 PR 상태는 "없음"이다(Q40).
8. **Linear 갱신.** 런 시작 때 티켓 상태를 Workspace 설정에서 고른 "In Progress" 상태로 바꾼다. 런이 끝나면 결과 댓글(요약 결과, 에이전트 결과, PR 상태, PR 링크)을 단다. 그 뒤 상태(In Review, Done)는 Linear의 GitHub 연동에 맡긴다(Q41, ADR 0001).
9. **워크트리 정리.** 워크트리를 지울지는 4.2 요약 계산 표가 정한다. Merged·Failed는 아래 예외를 빼면 런이 끝나면 바로 지우고, Human Check는 PR이 병합되거나 닫힐 때까지 남긴다. 러너 화면에 남은 워크트리 수를 보여 준다(Q44). 브랜치는 지우지 않는다(research 0002 A.7, 어댑터 초안 `removeWorktree`).
   - **시간 초과 예외.** 에이전트 결과가 시간 초과나 입력 기다리다 멈춤이고 PR이 열려 있으면 요약 결과는 Failed이지만, PR과 워크트리는 Human Check처럼 PR이 병합되거나 닫힐 때까지 남긴다(Q51).
   - **러너 연결 끊김 예외.** 에이전트 결과가 러너 연결 끊김이면 워크트리를 자동으로 지우지 않는다. 러너가 돌아온 뒤 사람이 정한다. 1단계에는 지우기 버튼이 없고, Run 상세에 "사람이 지워야 함"을 보이며 Runners의 남은 워크트리 수에 센다. 사람이 러너에서 직접 지우면 worker가 다음 러너 확인 때 워크트리가 사라진 것을 보고 지운 시각을 기록한다(Q75). Q64("다시 Online이면 worker가 지운다")는 이것으로 대체했다.
   - **PR을 남긴 런 이후.** PR 상태와 요약 결과는 바꾸지 않는다. Human Check 런과 PR 열린 시간 초과·입력 기다리다 멈춤 런은 그 뒤 PR이 사람 손으로 병합되거나 닫히면 이후 PR 상태로 런에 따로 기록하고 워크트리를 지운다(Q51·Q54·Q69).
10. **통계.** Stats 화면에서 처리량, 요약 결과 분포(Merged / Human Check / Failed)와 Failed의 두 축 조합별 수(Q71), 리드 타임, Human Check 뒤 병합 비율을 러너·트래커 프로젝트·에이전트별로 본다(티켓 0002, Q54). 리드 타임은 할당(Queued 포함)부터 런 종료까지이고, 대기 시간(할당~시작)과 실행 시간(시작~종료)을 나눠 보여 준다(Q59).

## 4. 도메인 규칙

### 4.1 런의 상태

런 상태는 Queued, Running, Waiting for Input, Disconnected, Ended 다섯이다(Q55·Q67, GLOSSARY). 화면에서 Disconnected는 "연결 끊김"으로 쓴다.

```
(할당) ──► Queued ──► Running ◄──────────► Waiting for Input
                       ▲   │                 ▲   │
            다시 연결  │   │ ssh 5분   다시  │   │ ssh 5분
                       │   ▼ 연속 실패 연결  │   ▼ 연속 실패
                      Disconnected ──────────┘   │
                           ▲                     │
                           └─────────────────────┘

Running | Waiting for Input | Disconnected ──► Ended
Ended ── 에이전트 결과 + PR 상태 ──(계산)──► 요약 결과: Merged | Human Check | Failed
```

- Running과 Waiting for Input은 ssh가 5분 동안 계속 실패하면 Disconnected가 된다. Disconnected는 다시 닿았을 때 에이전트가 돌고 있으면 Running으로, 입력을 기다리고 있으면 Waiting for Input으로 돌아간다(Q67).
- 한 티켓에 동시에 도는(Queued, Running, Waiting for Input, Disconnected인) 런은 하나다. Ended 뒤 새 런은 가능하다(Q45·Q74).
- Disconnected 런은 러너의 capacity를 계속 차지한다(Q74).
- 실패한 런은 자동으로 다시 시도하지 않는다(GLOSSARY Failed, Q47).
- 런은 에이전트 프로세스 종료, 최대 실행 시간 초과(Disconnected 동안 지난 경우 포함), 워크트리 사라짐으로 Ended가 된다(Q39·Q49·Q67).
- Waiting for Input과 Disconnected도 최대 실행 시간에 들어간다(Q52·Q67).

### 4.2 두 축과 요약 계산 표

런이 끝날 때 두 축을 한 번 기록한다(ADR 0004, Q66). 둘 다 바꾸지 않는다(Q69).

- **에이전트 결과**: 정상 종료, 오류 종료, 시간 초과, 입력 기다리다 멈춤, 러너 연결 끊김, 워크트리 없음(Q70). 뜻은 [GLOSSARY](../../GLOSSARY.md)를 따른다.
- **PR 상태**: 없음, 열림, 병합됨, 닫힘(병합 없이). 런이 끝난 때의 값이다. 그 뒤 사람이 병합하거나 닫은 것은 이후 PR 상태로 따로 기록한다(Q54·Q69).

요약 결과(Merged / Human Check / Failed)와 워크트리 처리는 두 축에서 이 표로 계산한다. 둘 다 저장하지 않고 필요할 때 계산한다(Q66·Q71·Q76). 워크트리를 실제로 지운 시각만 기록한다(Q75).

| 에이전트 결과                 | PR 상태  | 요약 결과   | 워크트리                                           |
| ----------------------------- | -------- | ----------- | -------------------------------------------------- |
| 시간 초과, 입력 기다리다 멈춤 | 열림     | Failed      | PR이 병합되거나 닫힐 때까지 남김                   |
| 시간 초과, 입력 기다리다 멈춤 | 그 밖    | Failed      | 바로 지움                                          |
| 러너 연결 끊김                | 무엇이든 | Failed      | 자동으로 지우지 않음, 러너가 돌아온 뒤 사람이 정함 |
| 워크트리 없음                 | 무엇이든 | Failed      | 지울 것이 없음                                     |
| 정상 종료, 오류 종료          | 병합됨   | Merged      | 바로 지움                                          |
| 정상 종료, 오류 종료          | 열림     | Human Check | PR이 병합되거나 닫힐 때까지 남김                   |
| 정상 종료, 오류 종료          | 닫힘     | Failed      | 바로 지움                                          |
| 정상 종료, 오류 종료          | 없음     | Failed      | 바로 지움                                          |

- 표는 위에서부터 처음 맞는 줄을 쓴다. 에이전트 결과 여섯과 PR 상태 넷의 모든 조합이 한 줄에 맞는다.
- 요약 결과는 이전 판정 표와 최대한 같은 값이 나온다. 다른 곳은 하나다. 이전에는 ssh 5분 연속 실패면 바로 Failed(러너 연결 끊김)였지만, 이제는 Disconnected를 거쳐 다시 닿으면 보통 런처럼 Merged나 Human Check로도 끝날 수 있다(Q67). 이전의 Failed 사유는 두 축으로 옮겼다: 시간 초과 → 에이전트 결과 시간 초과·입력 기다리다 멈춤, 러너 연결 끊김 → 최대 실행 시간이 지날 때까지 돌아오지 않았으면 에이전트 결과 러너 연결 끊김, 워크트리가 사라졌으면 워크트리 없음, PR이 닫힘 → PR 상태 닫힘, PR 없음 → 정상 종료 + 없음, 에이전트 오류 → 오류 종료 + 없음. 따로 저장하는 Failed 사유는 없다(Q71).
- 종료 코드는 요약 결과를 바꾸지 않는다. 오류 종료에 PR이 열려 있으면 요약은 Human Check이고, 화면의 두 칸에 "오류 종료"와 "열림"이 함께 보여 그 조합이 숨지 않는다(Q66, Q62를 대체).
- 시간 초과 런의 워크트리 예외(Q51)와 러너 연결 끊김 런의 워크트리 예외(Q67·Q75)는 요약 결과를 바꾸지 않는다.
- 같은 브랜치에 PR이 여럿이면 가장 최근 것을 쓰고, `isCrossRepository: false`, `headRepository`, `baseRefName`을 함께 확인한다(research 0002 C.2).
- PR 상태에는 PR `state`/`merged`만 쓴다. CI 상태는 화면 보조 정보다(research 0002 C.4).
- 요약 결과는 계산 함수 하나로만 정한다([CODING_STANDARDS](../../CODING_STANDARDS.md)). 화면·통계·worker가 각자 두 축을 해석하지 않는다(Q76).

### 4.3 범위 규칙

- Tracker Connection과 Runner는 설치 단위 자원이고 여러 개다. Workspace, Mapping, Auto-assign Label, 최대 실행 시간, "In Progress" 상태 선택은 Workspace 안에 있다(ADR 0006·0007, Q39·Q41).
- 트래커 프로젝트 하나는 Workspace 하나에만 속한다(ADR 0006).
- 러너의 capacity는 모든 Workspace의 런이 함께 쓴다(ADR 0006).
- Mapping은 트래커 프로젝트를 러너 쪽 프로젝트·에이전트와 잇고, 러너는 할당 때 고른다(Q53).

## 6. 외부 계약 요약

자세한 내용과 출처는 research [0002](../research/0002-external-contracts.md)에 있다. 어댑터 타입은 그 문서의 「어댑터 인터페이스 초안」을 출발점으로 쓴다.

- **Orca**: `--json` 봉투(`ok`, `result`, `error.code`). `orca worktree create --branch --agent --prompt --surface terminal --no-parent --json`으로 시작하고, `orca worktree ps --json`으로 진행을 보고, `orca worktree rm`으로 지운다. 워크트리는 `worktreeId`(`<repoId>::<path>`)로 저장한다. 응답을 잃으면 `--retry-launch <operationId>`로 다시 보낸다. 매핑의 러너 쪽 프로젝트 키는 `projectId`(`github:<owner>/<repo>`)다(A.4~A.7).
- **Linear**: 개인 API 키(`Authorization: <API_KEY>`)를 권한다. webhook은 운영자가 Linear 설정에서 손으로 만들고 signing secret을 붙여 넣는다. `Linear-Signature`는 원문 바이트의 HMAC-SHA256, 타임스탬프는 1분 안. 응답은 5초 안에 200, 재전송이 있으니 `Linear-Delivery`로 중복을 거른다. 상태는 팀마다 다르다(B.1~B.4).
- **GitHub**: GraphQL `pullRequests(headRefName:)` 1점 쿼리로 PR 상태를 본다. fine-grained PAT의 읽기 권한(Metadata, Pull requests, Commit statuses)이면 PR 상태를 정하는 데 충분하다(C.2~C.5).

## 7. 데이터와 보관

- 티켓의 상태와 내용은 트래커가 기준이다. 오케스트레이터는 런과 통계용 이력만 저장한다(ADR 0001).
- 저장소는 SQLite(WAL) 파일 하나이고 web과 worker가 함께 쓴다(ADR 0002).
- 런이 도는 동안의 로그는 저장하지 않는다. 런이 끝날 때 마지막 200줄만 저장한다(Q46).
- 토큰(Linear API 키, webhook signing secret, GitHub 토큰)은 DB에 암호화해 저장한다. `.env`에는 부팅 최소값(포트, 데이터 경로, 암호화 키, 바인딩 주소)만 둔다(ADR 0005). 지금 `.env.example`에 있는 토큰 변수(`LINEAR_API_KEY`, `LINEAR_WEBHOOK_SECRET`, `GITHUB_TOKEN`)는 부팅 설정을 읽는 구현 티켓에서 뺀다(Q58).

## 8. 보안

- 웹 서버는 기본으로 `127.0.0.1`에 바인딩한다(운영자 결정, `.env.example` `WEB_HOST`). research 0001 「남은 위험」은 `srvx`가 기본으로 모든 인터페이스에서 들으니 바인딩 주소를 정해야 한다고 적었다.
- Linear webhook은 HMAC 서명과 타임스탬프를 검증하고, 검증에 실패한 요청은 이벤트가 되지 못한다(research 0002 B.2).
- webhook을 밖에 여는 방법은 Tailscale Funnel, Cloudflare Tunnel, 리버스 프록시 중 운영자가 고른다(ADR 0005).
- ssh로 넘기는 `--prompt`(티켓 본문)는 원격 셸이 한 번 더 해석하므로 인자를 이스케이프해야 한다(research 0002 A.5·A.8).
- 저장소·문서·로그 예시에 운영자 환경 값을 넣지 않는다(ADR 0005, AGENTS.md).

## 9. 배포와 업그레이드

- npm 패키지 하나와 CLI로 배포하고 macOS·Linux에서 네이티브로 돈다. Docker는 1단계에서 뺀다(ADR 0005, Q47).
- 릴리스는 SemVer와 Changesets, 1.0 전에는 0.x(ADR 0005).
- Node는 `node_modules` 안의 `.ts`에 타입 스트리핑을 하지 않으므로, 배포하려면 worker와 공유 패키지를 JS로 빌드해야 한다. 웹은 이미 `dist`로 빌드된다(research [0001](../research/0001-web-stack-spike.md) 「남은 위험」).
- 업데이트 시 DB 마이그레이션을 자동으로 실행한다. worker는 언제 재시작돼도 SQLite 상태로 이어서 폴링한다(ADR 0002·0005).
- 러너 필수 조건. 온보딩과 Settings의 러너 확인이 아래를 점검한다.
  - Orca 상시 서비스(Q43). 설치 명령은 `orca serve service install`이다. Orca 1.4.258에는 `--supervise` 플래그가 없고 서비스가 안에서 스스로 다시 띄운다. 러너의 PATH에 `orca`가 없으면 `--command <orca 절대 경로>`를 함께 준다(2026-11-17 검증).
  - 비대화형 ssh 세션에서 동작하는 GitHub 인증. 에이전트가 러너에서 push하고 PR을 열어야 PR 상태를 정할 수 있다. 대화형 터미널에서는 되는 인증도 비대화형 ssh 세션에서는 안 될 수 있다(gh 토큰 무효, macOS 키체인 잠김, GitHub용 ssh 키 없음, 2026-11-17 검증).
- 이 제품은 각 사용자 프로젝트의 에이전트 설정을 고치지 않는다(ADR 0004). 에이전트가 오케스트레이터가 정한 브랜치가 아닌 브랜치로 PR을 열면(브랜치 이름을 바꾼 경우 포함) 2순위인 티켓 키 검색에 기대야 한다. 이때 PR 제목·본문에 티켓 키가 없으면 PR을 찾지 못해 PR 상태가 "없음"이 되거나, 이름을 바꾸며 닫힌 옛 PR을 잡아 "닫힘"이 된다(research 0006 17절). 그래서 온보딩 Mapping 단계와 README에서 에이전트가 PR 제목에 티켓 키를 넣도록 프로젝트 지침에 적기를 권한다.
