# 1단계(0.1.0) 스펙

1단계 구현의 기준 문서다. 흩어진 결정(GLOSSARY, ADR 0001~0007, research 0001·0002, 티켓 0001~0003, 2026-11-17 운영자 결정 Q39~Q48)을 한곳에 묶는다. 이 문서는 새 결정을 만들지 않는다. 근거 문서에 없는 것은 「열린 질문」에 남긴다. 다음 단계에서 이 문서를 `docs/tickets/` 티켓으로 쪼갠다.

용어는 [GLOSSARY](../../GLOSSARY.md)를 따른다.

## 1. 목표와 완료 기준

목표: 트래커의 티켓을 러너에 맡기고, 런의 결과를 판정해 화면과 통계로 보여 주는 셀프호스팅 제품의 첫 릴리스를 낸다(ADR [0005](../adr/0005-self-hosted-product.md)).

완료 기준(Q48):

- 테스트용 Linear 워크스페이스의 티켓 하나에 Auto-assign Label을 붙이는 것만으로 러너에서 처리된다.
- 그 런이 Merged / Human Check / Failed 중 하나로 판정되고 화면과 통계에 나타난다.
- 위를 npm CLI로 설치한 오케스트레이터로 해낸다. 그러면 0.1.0으로 릴리스한다.

## 2. 범위와 제외

범위:

- 온보딩, Tracker Connection(Linear), GitHub 토큰, Runner(Orca over ssh) 등록, Workspace, Mapping, Auto-assign Label
- 수동·자동 할당, FIFO 대기열, 런 시작·감시·종료, 결과 판정, Linear 갱신, 워크트리 정리
- 화면: 홈, Tickets, Runs, Run 상세, Runners, Stats, Settings, 온보딩(티켓 [0002](../tickets/0002-html-prototype.md), 시안 B, ADR [0007](../adr/0007-ui-list-detail-panel.md))
- npm 패키지와 CLI(`init`, `start`, launchd·systemd 등록), 업데이트 시 DB 마이그레이션 자동 실행(ADR 0005)

제외(Q47): 다중 사용자, Docker 배포, Linear 외 트래커, Orca 외 러너, 토큰·비용 통계, 자동 재시도, Workspace별 우선순위, 모바일 레이아웃, 라이트 모드.

## 3. 사용자 흐름

1. **온보딩.** 첫 진입 즉시 사이드바 없는 전체 화면으로 뜬다. 트래커 연결 → GitHub 토큰 → 첫 러너 등록과 ssh 확인 → 첫 Workspace(트래커 프로젝트 고르기) → 첫 Mapping 순서이고, 모든 단계가 필수이며 확인이 성공해야 다음으로 간다(ADR 0005·0007). 러너 등록 단계는 러너에 Orca 상시 서비스(`orca serve service install --supervise`)가 있는지 확인하고, 없으면 설치 명령을 안내한다. orca 실행 파일 경로는 러너 설정으로 받는다(Q43, research [0002](../research/0002-external-contracts.md) A.3·A.8).
2. **할당.** 운영자가 Tickets 화면에서 직접 하거나(수동), 티켓에 Auto-assign Label이 붙으면 오케스트레이터가 한다(자동). 자동 할당은 Linear webhook으로 감지하고, 놓친 이벤트는 주기적 폴링으로 맞춘다(ADR [0001](../adr/0001-tracker-is-source-of-truth.md)). 할당 조건은 "`data.labelIds`에 Auto-assign Label이 있고, 그 티켓에 진행 중이거나 Queued인 런이 없다"로 잡는다(research 0002 B.2, Q45).
3. **대기열.** 맞는 러너에 남은 capacity가 없으면 런은 Queued가 된다. 대기열은 설치 전체에 하나이고 들어온 순서(FIFO)로 꺼낸다(ADR [0006](../adr/0006-workspace-scoping.md)).
4. **런 시작.** worker가 ssh로 러너에 `orca worktree create`를 보내 워크트리를 만들고 에이전트를 띄운다. 오케스트레이터가 브랜치 이름을 정하고(예: `factory/<티켓 키>-<런 번호>`, Q40), 에이전트는 항상 `--surface terminal`로 띄운다(Q42). 에이전트에게는 티켓만 지시로 준다(GLOSSARY Agent, ADR [0004](../adr/0004-agent-merges-its-own-pr.md)).
5. **런 진행.** worker가 러너를 폴링해 진행을 본다(ADR [0002](../adr/0002-start-web-plus-worker-daemon.md), research 0002 A.6 `orca worktree ps`). 운영자가 Run 상세를 열면 그때 ssh로 로그 꼬리를 가져와 보여 주고 저장하지 않는다(Q46).
6. **종료 감지.** 에이전트 프로세스가 끝나면 런이 끝난다. 최대 실행 시간(기본 2시간, Workspace별 설정)을 넘기면 에이전트를 멈추고 Failed(사유: 시간 초과)로 끝낸다(Q39).
7. **결과 판정.** 런이 끝난 때의 PR 상태로 판정한다(ADR 0004, 4절 판정 표). 런과 PR은 1순위 오케스트레이터가 정한 브랜치의 PR, 없으면 PR 제목·본문의 티켓 키로 잇고, 둘 다 없으면 "PR 없음"이다(Q40).
8. **Linear 갱신.** 런 시작 때 티켓 상태를 Workspace 설정에서 고른 "In Progress" 상태로 바꾼다. 런이 끝나면 결과 댓글(결과, PR 링크, 실패 사유)을 단다. 그 뒤 상태(In Review, Done)는 Linear의 GitHub 연동에 맡긴다(Q41).
9. **워크트리 정리.** Merged·Failed는 런이 끝나면 바로 지운다. Human Check는 PR이 병합되거나 닫힐 때까지 남긴다. 러너 화면에 남은 워크트리 수를 보여 준다(Q44). 브랜치는 지우지 않는다(research 0002 A.7, 어댑터 초안 `removeWorktree`).
10. **통계.** Stats 화면에서 처리량, 결과 분포(Merged / Human Check / Failed), 리드 타임을 러너·트래커 프로젝트·에이전트별로 본다(티켓 0002).

## 4. 도메인 규칙

### 4.1 런의 상태

```
(할당) ──► Queued ──► 실행 중 ──► 끝남 ──► Merged | Human Check | Failed
              └── capacity가 있으면 바로 실행 중
```

- 한 티켓에 동시에 도는(또는 Queued인) 런은 하나다. 끝난 뒤 새 런은 가능하다(Q45).
- 실패한 런은 자동으로 다시 시도하지 않는다(GLOSSARY Failed, Q47).
- 런의 끝은 에이전트 프로세스 종료 또는 최대 실행 시간 초과다(Q39).

### 4.2 결과 판정 표

런이 끝난 때 한 번 판정한다(ADR 0004, research 0002 C.2). [Merged](../../GLOSSARY.md), [Human Check](../../GLOSSARY.md), [Failed](../../GLOSSARY.md)는 GLOSSARY 정의를 따른다.

| 런이 끝난 방식·PR 상태             | 결과        | Failed 사유    |
| ---------------------------------- | ----------- | -------------- |
| 최대 실행 시간 초과                | Failed      | 시간 초과      |
| 에이전트 종료, PR `MERGED`         | Merged      | —              |
| 에이전트 종료, PR `OPEN`           | Human Check | —              |
| 에이전트 종료, PR `CLOSED`(미병합) | Failed      | PR이 닫힘      |
| 에이전트 종료, PR 없음             | Failed      | 열린 질문 참고 |
| 러너 연결 끊김                     | Failed      | 러너 연결 끊김 |

- 같은 브랜치에 PR이 여럿이면 가장 최근 것을 쓰고, `isCrossRepository: false`, `headRepository`, `baseRefName`을 함께 확인한다(research 0002 C.2).
- 판정에는 PR `state`/`merged`만 쓴다. CI 상태는 화면 보조 정보다(research 0002 C.4).

### 4.3 범위 규칙

- Tracker Connection과 Runner는 설치 단위 자원이고 여러 개다. Workspace, Mapping, Auto-assign Label, 최대 실행 시간, "In Progress" 상태 선택은 Workspace 안에 있다(ADR 0006·0007, Q39·Q41).
- 트래커 프로젝트 하나는 Workspace 하나에만 속한다(ADR 0006).
- 러너의 capacity는 모든 Workspace의 런이 함께 쓴다(ADR 0006).

## 6. 외부 계약 요약

자세한 내용과 출처는 research [0002](../research/0002-external-contracts.md)에 있다. 어댑터 타입은 그 문서의 「어댑터 인터페이스 초안」을 출발점으로 쓴다.

- **Orca**: `--json` 봉투(`ok`, `result`, `error.code`). `orca worktree create --branch --agent --prompt --surface terminal --no-parent --json`으로 시작하고, `orca worktree ps --json`으로 진행을 보고, `orca worktree rm`으로 지운다. 워크트리는 `worktreeId`(`<repoId>::<path>`)로 저장한다. 응답을 잃으면 `--retry-launch <operationId>`로 다시 보낸다. 매핑의 러너 쪽 프로젝트 키는 `projectId`(`github:<owner>/<repo>`)다(A.4~A.7).
- **Linear**: 개인 API 키(`Authorization: <API_KEY>`)를 권한다. webhook은 운영자가 Linear 설정에서 손으로 만들고 signing secret을 붙여 넣는다. `Linear-Signature`는 원문 바이트의 HMAC-SHA256, 타임스탬프는 1분 안. 응답은 5초 안에 200, 재전송이 있으니 `Linear-Delivery`로 중복을 거른다. 상태는 팀마다 다르다(B.1~B.4).
- **GitHub**: GraphQL `pullRequests(headRefName:)` 1점 쿼리로 PR 상태를 본다. fine-grained PAT의 읽기 권한(Metadata, Pull requests, Commit statuses)이면 판정에 충분하다(C.2~C.5).

## 7. 데이터와 보관

- 티켓의 상태와 내용은 트래커가 기준이다. 오케스트레이터는 런과 통계용 이력만 저장한다(ADR 0001).
- 저장소는 SQLite(WAL) 파일 하나이고 web과 worker가 함께 쓴다(ADR 0002).
- 런이 도는 동안의 로그는 저장하지 않는다. 런이 끝날 때 마지막 200줄만 저장한다(Q46).
- 토큰(Linear API 키, webhook signing secret, GitHub 토큰)은 DB에 암호화해 저장한다. `.env`에는 부팅 최소값(포트, 데이터 경로, 암호화 키 등)만 둔다(ADR 0005).

## 8. 보안

- 웹 서버는 기본으로 `127.0.0.1`에 바인딩한다(research 0001 「남은 위험」, `.env.example` `WEB_HOST`).
- Linear webhook은 HMAC 서명과 타임스탬프를 검증하고, 검증에 실패한 요청은 이벤트가 되지 못한다(research 0002 B.2).
- webhook을 밖에 여는 방법은 Tailscale Funnel, Cloudflare Tunnel, 리버스 프록시 중 운영자가 고른다(ADR 0005).
- ssh로 넘기는 `--prompt`(티켓 본문)는 원격 셸이 한 번 더 해석하므로 인자를 이스케이프해야 한다(research 0002 A.5·A.8).
- 저장소·문서·로그 예시에 운영자 환경 값을 넣지 않는다(ADR 0005, AGENTS.md).

## 9. 배포와 업그레이드

- npm 패키지 하나와 CLI로 배포하고 macOS·Linux에서 네이티브로 돈다. Docker는 1단계에서 뺀다(ADR 0005, Q47).
- 릴리스는 SemVer와 Changesets, 1.0 전에는 0.x(ADR 0005).
- Node는 `node_modules` 안의 `.ts`에 타입 스트리핑을 하지 않으므로, 배포하려면 worker와 공유 패키지를 JS로 빌드해야 한다. 웹은 이미 `dist`로 빌드된다(research [0001](../research/0001-web-stack-spike.md) 「남은 위험」).
- 업데이트 시 DB 마이그레이션을 자동으로 실행한다. worker는 언제 재시작돼도 SQLite 상태로 이어서 폴링한다(ADR 0002·0005).
- 러너에는 Orca 상시 서비스가 필요하다(Q43).

## 11. 열린 질문

근거 문서로 답이 나오지 않는 것이다. 티켓으로 쪼개기 전에 운영자가 정한다.

1. **PR 없음의 Failed 사유.** GLOSSARY의 사유(에이전트 오류, 러너 연결 끊김, PR이 닫힘, 시간 초과) 중 에이전트가 PR 없이 정상 종료한 경우를 어느 사유로 둘지, 사유를 따로 둘지(research 0002 초안은 `no-pr`).
2. **러너 연결 끊김의 기준.** 런 중 ssh가 몇 번, 얼마 동안 실패하면 Failed(러너 연결 끊김)로 볼지. 끊김이 최대 실행 시간보다 짧게 끝나면 이어서 볼지.
3. **시간 초과 런의 PR.** 시간 초과로 멈춘 런이 PR을 열어 두었을 때 그 PR과 워크트리를 어떻게 할지(Q44는 Failed 워크트리를 바로 지운다).
4. **사람 대기.** 에이전트가 권한 프롬프트 등에서 사람을 기다릴 때(`--agent-wait`, research 0002 A.6) 시간 초과까지 기다릴지, 화면에 따로 알릴지.
5. **러너 고르기.** 같은 러너 쪽 프로젝트가 여러 러너에 있을 때 어느 러너에 할당할지. Mapping이 러너를 고르는지, 러너 쪽 프로젝트만 고르는지.
6. **Human Check 이후.** PR이 나중에 병합되거나 닫히면 런 결과(Human Check)를 그대로 둘지, 통계에 반영할지. ADR 0004는 런 종료 시 판정만 정한다.
7. **Run 상태 이름.** GLOSSARY에는 Queued만 있다. 실행 중·끝남 상태를 GLOSSARY에 더할지.
8. **어댑터와 CLI의 위치.** Tracker·Runner·GitHub 어댑터와 CLI를 어느 패키지에 둘지(`packages/core` 안, 별도 패키지, `apps/worker` 안).
9. **ADR 0001 문구.** ADR 0001은 "PR이 생기면" 트래커를 갱신한다고 적는데, Q41은 런 시작·종료 때만 갱신하고 이후 상태는 Linear GitHub 연동에 맡긴다. ADR 0001을 고칠지.
10. **`.env.example`.** 지금 `LINEAR_API_KEY`, `LINEAR_WEBHOOK_SECRET`, `GITHUB_TOKEN`을 담고 있는데, ADR 0005는 토큰을 DB에 암호화해 두고 `.env`에는 부팅 최소값만 둔다. 구현 때 이 파일을 정리할지.
11. **리드 타임 정의.** Stats의 리드 타임을 무엇부터 무엇까지로 셀지(할당~종료, Queued 포함 여부 등).
12. **수동 할당과 Mapping.** 수동 할당 때 Mapping의 러너 쪽 프로젝트·에이전트를 그대로 쓰는지, 운영자가 바꿀 수 있는지.
