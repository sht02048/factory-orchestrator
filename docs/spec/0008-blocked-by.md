# 0008 먼저 끝나야 하는 티켓과 우선순위 대기열

## 목표

Linear의 blocked by 관계를 지켜, 먼저 끝나야 하는 티켓이 끝난 뒤에 런이 저절로 시작하게 한다. 대기열은 Linear 우선순위 순서로 세운다.

## 운영자 결정 (2026-11-21)

- **B1** 선행 티켓이 끝났다 = Linear 상태 종류가 completed(Done 등).
- **B2** 선행 티켓이 canceled 면 끝난 것으로 보지 않는다. 뒤 티켓은 기다리고 "선행 티켓 X 가 취소됐어요"(멈춘 기다림). 풀기는 기다리지 않고 시작 또는 Linear 에서 관계 삭제.
- **B3** blocked-by 가 있는 티켓도 맡길 수 있다. 런은 Queued, 대기 이유 "X 를 기다려요", 러너 자리를 차지하지 않는다. 선행 티켓이 모두 끝나면 보통 Queued 처럼 자리가 나는 대로 저절로 시작.
- **B4** Auto-assign 레이블로 맡긴 런도 같다.
- **B5** 기다리지 않고 시작: 기다리는 런에서 확인을 받고 보통 Queued 줄에 세운다(런 쓰기 동작, 0156 중복 요청 규칙을 따른다).
- **B6** 대기열 순서: Linear 우선순위(Urgent→High→Medium→Low→없음), 같으면 먼저 온 순서. 0155 의 러너별 줄 안에서 적용. 시작한 런은 멈추지 않는다. Dashboard 카드에는 우선순위를 표시하지 않는다(Tickets 목록에는 우선순위 열을 둔다).
- **B7** 같은 Linear 연결이면 어느 팀·프로젝트의 선행 티켓도 상태를 읽어 기다린다. 읽지 못하면 끝나지 않은 것으로 보고 "X 를 읽지 못했어요"(멈춘 기다림).
- **B8** 순환(서로 기다림)은 맡길 때와 관계를 새로 읽을 때 찾아 "X 와 서로 기다려요"(멈춘 기다림). 저절로 풀지 않는다.
- **B9** webhook 이 켜져 있으면 선행 티켓 상태 변경을 받는 즉시 반영, 그와 별개로 기다리는 런이 있는 동안 1분마다 그 선행 티켓들만 다시 읽는다.
- **B10** Queued 중 관계 추가·삭제는 바로 반영. Running 중 새 관계는 무시. 선행 티켓이 다시 열리면(Done→진행) 시작한 런은 그대로, 아직 Queued 인 런은 다시 기다린다.
- **B11** 화면(0160): Tickets 목록의 기다림 표시와 우선순위 열, 상세 패널의 "먼저 끝나야 하는 티켓"/"이 티켓을 기다리는 티켓", Dashboard Queued 카드(B 안: 번호·제목 두 줄, 선행 티켓 칩—점 색이 그 티켓 상태, 끝난 것은 취소선, 취소는 빨간 칩, 멈춘 기다림은 빨간 테두리), Run 상세의 대기 이유·선행 목록·기다리지 않고 시작. 관계 그래프 화면은 만들지 않는다. Dashboard 카드의 번호·제목 두 줄은 모든 카드에 적용.

## 두 티켓의 경계

- [0159](../tickets/0159-blocked-by-queue.md): tracker, 저장, 대기열, 다시 읽기, 멈춘 기다림 판단, 기다리지 않고 시작의 서버 함수와 MCP 도구, 로더와 MCP 읽기의 대기 이유, 데모. 화면은 지금 Queued 문구 자리에 이유 문장만 나오게 한다.
- [0160](../tickets/0160-blocked-by-ui.md): B11 화면 전부.

## 구현에서 정한 것

- 런마다 선행 티켓과 마지막으로 읽은 상태를 `run_blockers`에 저장한다. 우선순위와 읽은 때는 `runs`에 둔다.
- 아직 관계를 읽지 않은 런은 시작하지 않는다. worker는 시작 명령을 보내기 직전에도 10초보다 오래된 관계를 다시 읽는다.
- Linear webhook에는 관계 변경 이벤트가 없다. 관계 변경은 그 티켓의 Issue 이벤트, 1분 폴링, 시작 직전 읽기로 반영한다.
- 시작 명령을 보낸 런은 기다림 판단에서 뺀다. 러너에 이미 떠 있을 수 있기 때문이다.

## 완료 기준

- 기다리는 런은 러너 자리를 차지하지 않고, 선행 티켓이 모두 끝나면 저절로 시작한다.
- 취소·읽기 실패·순환은 멈춘 기다림으로 남고, 기다리지 않고 시작으로 풀린다.
- 러너별 줄 안에서 우선순위 순서로 시작하고, 고정 러너 규칙(0155)을 지킨다.
- 대기 이유가 app 로더와 MCP 읽기에 실린다.

## 위험

- 이어서 맡긴 런도 같은 규칙으로 기다린다. 결정에 따로 적히지 않아 B3을 그대로 적용했고, 기다리지 않고 시작으로 풀 수 있다.
- 자리만 기다리는 런의 우선순위는 webhook이 없으면 맡길 때 읽은 값이다. B9가 폴링을 기다리는 런으로 한정하기 때문이다.
- 순환 찾기는 한 선행 티켓에서 50개까지만 따라간다. 그보다 긴 순환은 멈춘 기다림 대신 보통 기다림으로 보인다.
