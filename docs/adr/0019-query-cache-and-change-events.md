# 웹 데이터는 TanStack Query 하나에 담고, DB의 변경 기록과 SSE로 무효화한다

웹 화면의 클라이언트 캐시는 라우터 로더 캐시 하나다. 쓰기 뒤에는 필터 없는 `router.invalidate()`가 루트·셸·지금 화면을 모두 다시 읽고, Settings·Tickets면 트래커도 다시 기다린다. 반대로 worker·트래커 webhook·MCP·다른 기기가 바꾼 것은 열린 화면에 닿지 않아, Dashboard 밖의 화면은 머무는 동안 끝없이 낡은 값을 보인다(research [0016](../research/0016-web-data-loading.md)). 운영자는 다른 기기에서 사설망 너머로(왕복 20~200ms) 쓰는 일이 많아, 왕복 하나가 화면 이동 체감에 그대로 더해진다. TanStack Query 조사(research [0015](../research/0015-tanstack-query.md)) 뒤 운영자와 정했다(2026-11-19, 스펙 [0003](../spec/0003-query-cache.md)의 C1~C14).

## 결정

- **`_app` 데이터 화면과 셸의 클라이언트 캐시는 TanStack Query 하나다.** Dashboard, Tickets, Runs, Run 상세, Runners, Stats, Settings와 셸(레일 배지, Workspace 목록)이 대상이다. 신선도는 Query의 `staleTime`이 정한다.
- **라우터 로더는 Query를 부른다.** 로더와 컴포넌트가 같은 `queryOptions`를 쓰고, 로더는 `apps/web/src/query/route-query.ts`의 `loadRouteQuery`(트래커 query는 `loadCachedRouteQuery`)로 읽는다. 캐시가 있으면 기다리지 않고 넘어가고, 클라이언트에서 화면에 들어올 때는 5초 안에 미리 읽은 데이터가 아니면 뒤에서 새로 읽는다(0117 계약, 스펙 0003 4.2). 서버 렌더와 hydration은 `@tanstack/react-router-ssr-query`가 맡고, `QueryClient`는 요청마다 `getRouter()` 안에서 만든다. 라우터 `defaultPreloadStaleTime`은 0이다(공식 권장, 0129). 라우터 로더로 남은 온보딩 route만 route 단위로 5초를 둔다.
- **`_app` 안에서 라우터를 다시 읽지 않는다.** 쓰기 뒤에는 바꾼 query key만 무효화한다. `router.invalidate()`는 루트(시간대 쿠키), 온보딩과 그 안의 러너 설정 흐름, 서버를 다시 읽지 않는 두 곳(Settings 상세의 문서 제목 따라가기, 셸 안 오류 화면의 다시 읽기)에만 남는다(스펙 0003 6절 5번).
- **셸 안 화면의 읽기 실패는 셸 안에 보인다.** `_app` 아래 화면 route는 모두 공용 오류 화면(`apps/web/src/shell/screen-error.tsx`)을 `errorComponent`로 쓴다. 레일은 남고, 화면 칸에 실패와 다시 읽기 단추가 보인다. 셸 자신의 읽기가 실패하면 지금처럼 루트 오류 화면이 대신한다.
- **루트와 온보딩·러너 설정 흐름은 라우터 로더로 남는다.** 루트는 시간대·제목 표시줄 쿠키와 온보딩 완료 확인을 읽는다. 앱 전체의 context라 주인이 라우터다. 온보딩과 러너 설정은 한 번 지나가는 흐름이라 캐시로 얻는 것이 없다.
- **바뀐 것은 DB의 변경 기록 표 `change_events`에 남긴다.** 무엇을 바꾸는 코드가 같은 트랜잭션에서 대상 종류·id·Workspace·시각을 한 줄 쓴다. web·worker·`ganger mcp` 중 누가 썼든 같은 표에 남는다.
- **web은 새 SSE 통로 `/api/change-events/stream`으로 그 줄을 보낸다.** 서버가 1초마다 표를 읽어 새 줄을 보내고, 브라우저는 대상에 맞는 query key만 무효화한다. 보이는 화면의 query만 다시 읽는다. 다시 연결하면 `Last-Event-ID`로 놓친 줄부터 받고, 그 번호로 이어 받을 수 없으면(이미 지워졌거나, DB를 되돌려 지금 번호보다 크면) 모든 query를 무효화한다. SSE가 끊긴 동안은 30초 폴링으로 버틴다. 숨은 탭은 연결을 닫고 다시 보이면 마지막 번호로 이어 받는다(운영자 결정 2026-11-20, HTTP/1.1 연결 수 한도 때문).

## 고려한 대안

- **라우터 캐시만 쓴다.** 새 의존성이 없다. 하지만 라우터 캐시는 route match 단위라, 한 화면의 일부(Tickets의 런 표시, Settings의 Mapping 한 칸)만 다시 읽을 수 없다. 화면 사이에 같은 데이터(Workspace 목록, 트래커 라벨)를 나눠 쓸 수도 없다. `router.invalidate()`에 필터를 다는 것으로는 "이 런이 바뀌었다"를 "이 화면들의 이 부분"으로 옮길 수 없다.
- **폴링만 한다.** 서버 쪽 일이 없다. 하지만 원격에서 화면마다 짧은 주기로 다시 읽으면 왕복과 트래커 읽기가 계속 쌓이고, 주기를 늘리면 데스크톱 알림(약 2초)과 화면이 어긋난다. 폴링은 SSE가 끊겼을 때의 대비로만 둔다(30초).
- **알림 사건 SSE를 다시 쓴다.** 이미 있는 통로다. 하지만 알림 사건은 운영자에게 알릴 일만 담고(GLOSSARY), 런 시작·상태 옮김·할당·설정 저장은 담지 않는다. 담으려면 알림 사건의 뜻을 바꿔야 하고, 데스크톱 앱이 같은 사건을 쓰고 나중에 모바일 푸시도 쓴다. 게다가 알림 사건은 Dashboard 로더를 다시 계산해 원인을 찾는 방식이라, 화면 무효화에 필요한 "무엇이 바뀌었나"를 바꾼 코드에서 바로 얻지 못한다.
- **DB를 혼자 여는 서버 프로세스를 둔다.** 운영자가 물었다. 그 프로세스가 모든 쓰기를 받으면 바뀜을 메모리에서 바로 알릴 수 있다. 이번에는 하지 않는다.
  - 지금은 web, worker, `ganger mcp` 세 프로세스가 SQLite 파일 하나를 직접 연다. 셋의 DB 호출이 모두 네트워크 호출이 되고, 트랜잭션 경계를 그 서버의 API로 다시 그어야 한다.
  - 데스크톱 앱, `ganger start`, 서비스 설치가 지켜볼 프로세스가 하나 늘어난다.
  - 그래도 다시 연결한 클라이언트에게 놓친 바뀜을 다시 보내려면 기록(replay log)이 필요하다. 그 기록은 결국 표 하나다.
  - Ganger가 서버 여러 대로 늘거나 DB를 따로 두게 되면 다시 본다.
- **web 서버를 메모리 허브로 둔다.** worker와 MCP가 바뀔 때마다 web에 알리고 web이 브라우저로 보낸다. web이 내려가 있던 동안의 바뀜을 잃고, MCP 프로세스가 web 주소를 알아야 하며, 다시 연결한 클라이언트에게 놓친 것을 다시 보낼 수 없다.

## 결과

- 웹에 `@tanstack/react-query`와 `@tanstack/react-router-ssr-query`가 들어온다(필요하면 pnpm peer 해석 때문에 `@tanstack/query-core`도 직접 의존성으로). devtools는 개발 빌드에만 싣는다.
- 열린 이슈 셋(research 0015 7절)이 우리 설정에서 재현되는지 PoC(티켓 0123)에서 먼저 본다. 재현되면 이 결정을 멈추고 다시 본다.
- DB에 `change_events` 표가 생긴다(one-way 마이그레이션). 바꾸는 코드는 모두 같은 트랜잭션에서 줄을 써야 하고, 빠뜨리면 그 바뀜은 30초 폴링이나 탭 복귀 때까지 화면에 닿지 않는다. 그래서 쓰는 곳마다 시험을 둔다.
- 줄은 하루 뒤 지운다. 하루보다 오래 끊겼던 클라이언트는 모든 query를 다시 읽는다.
- 쓰기 서버 함수는 지금처럼 `{ ok: false, reason }`을 돌려주고, 클라이언트 mutation이 이유가 담긴 오류로 바꾼다. 읽기는 실패하면 throw한다. 트래커 실패를 화면에 보이는 `Remote<T>` 데이터는 그대로다.
- 트래커 결과를 서버에 담아 두는 것(stale-while-revalidate)과 화면 이동 왕복 줄이기는 티켓 0122가 따로 맡는다. 이 ADR은 클라이언트 캐시와 무효화 통로만 정한다.
