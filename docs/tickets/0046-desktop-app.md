# 데스크톱 앱 (Electron 앱과 분리된 상시 서버)

> **보류(운영자 지시 2026-11-18).** 이 티켓은 0029의 서버 배포물에 기댄다. 0029가 web 운영 의존성까지 묶은 배포물을 만들었고(research 0012의 스파이크가 막힌 지점), Electron의 Node(`ELECTRON_RUN_AS_NODE`)로 그 배포물의 `start`가 도는 것을 확인했다. 보류를 풀 때까지 시작하지 않는다.

## 목표

운영자가 자기 노트북에서 저장소를 빌드하지 않고 데스크톱 앱으로 설치해 쓴다. 앱을 닫거나 업데이트해도 서버와 worker는 계속 돈다.

## 배경

research [0012](../research/0012-desktop-app-packaging.md) 5절의 운영자 결정(2026-11-18)을 따른다.

- ① Electron 앱(창·트레이·알림)과 ② 앱에서 분리된(detached) 서버·worker 프로세스로 나눈다. Orca 앱이 창과 별도의 상시 터미널 호스트를 두어 업데이트 뒤에도 세션이 이어지는 방식에서 옮겨 온 판단이다(research 0012 1절. Orca가 다시 붙는 방법은 확인하지 않았다).
- ③ 헤드리스 서비스(CLI `service install`, `apps/cli/src/service.ts`)는 그대로 둔다. 24시간 켜 두는 기계는 ③, 노트북에서 직접 쓰기는 ①+②다. ②와 ③은 같은 서버 코드(`apps/cli/src/start.ts`)를 띄우는 방식만 다르다.
- 도구는 Electron이다. Node 24와 `node:sqlite`가 그대로 돌고, 고치지 않은 CLI `start`를 Electron 안에서 띄웠다(research 0012 2절).

## 범위

- **①+② 구조.** 앱(①)은 창·트레이·알림만 맡고, 서버(②)는 `start`가 띄우는 web + worker다. 서버 코드는 ③과 공유하고, 앱 전용으로 갈라 쓰지 않는다. 앱은 0029의 서버 배포물(`pnpm run bundle`의 폴더)을 고치지 않고 리소스로 싣는다. 배포물에는 Node가 없어, ②를 띄울 Node(Electron의 Node 또는 따로 싣는 Node)는 아래 「②의 detach」에서 정한다.
- **②의 detach.** 앱이 ②를 앱 프로세스의 자식이 아니게 띄워, 앱이 끝나거나 다시 떠도 ②가 멈추지 않는다. Electron `runAsNode` fuse를 끌지, ②를 Node로 띄울 방법을 무엇으로 할지 여기서 정한다(research 0012 「남은 위험」).
- **재접속과 두 벌 실행 막기.** 앱은 열릴 때 home(`~/.factory-orchestrator` 또는 설정한 경로)의 잠금 파일·포트로 도는 ②를 찾아 붙고, 없을 때만 띄운다. 같은 home에 ②가 둘 뜨지 않게 하고, 같은 기계에 ③이 이미 돌면 ②를 띄우지 않고 ③에 붙는다. ③은 launchd·systemd가 다시 띄우므로(`apps/cli/src/service.ts`), ③에 붙었을 때 트레이는 상태만 보이고 켜고 끄기와 버전 교체는 하지 않는다. 앱에 실린 서버 코드와 ③의 버전이 다르면 알리기만 한다.
- **②의 감시.** ②가 실패로 끝났을 때 누가 다시 띄울지 정한다(앱이 열려 있을 때 앱, 로그인 때 실행 등록 여부).
- **②의 버전 교체.** 앱 업데이트로 서버 코드가 바뀌면 옛 ②를 멈추고 마이그레이션 뒤 새 ②를 띄운다. worker 두 벌이 같은 DB를 폴링하지 않게 한다. 도는 런은 러너에서 계속 돌고, 새 worker가 DB의 상태에서 이어서 감시한다(`apps/worker/src/worker.ts`). 교체하는 동안 실패한 webhook은 폴링 보정이 메운다(ADR 0001).
- **트레이.** ②의 상태(돌고 있음·멈춤·실패)를 보이고 켜고 끈다. 창을 닫아도 트레이에 남는다. 화면 문구는 메시지 파일로 둔다(ADR 0005).
- **자동 업데이트.** 앱을 GitHub Releases로 배포하고 자동 업데이트한다(research 0012 2절 「자동 업데이트」). 0031의 릴리스 흐름이 있으면 그 위에 더하고, 없으면 이 티켓이 Releases에 설치 파일을 올리는 흐름을 만든다.
- **지원 플랫폼**은 ADR 0005의 macOS·Linux다.
- README에 앱 설치와 ①+②·③ 중 무엇을 고를지 영어로 쓴다.

## 운영자 결정 필요

- **macOS 서명.** 운영자는 Apple Developer Program 회원이라 가입·비용은 막지 않는다. (1) 서명 인증서에 계정 이름이 보이는 것을 받아들일지(ADR 0005), (2) 서명 키를 공개 저장소 CI 시크릿에 둘지 운영자가 로컬에서 서명할지를 정해야 한다. 서명 키·팀 ID 같은 값은 저장소에 넣지 않는다. 답 전에는 서명 없이 만들고 서명 단계를 기본 동작으로 정하지 않는다.

## 완료 조건

- 앱을 끝내고 다시 여는 동안 Running 런의 상태가 Running으로 남고, 다시 연 앱이 같은 ②에 붙어 그 런을 보인다는 시험이 통과한다(②의 프로세스 ID가 바뀌지 않는다).
- 앱을 두 번 열거나 ③이 도는 기계에서 앱을 열어도 같은 home에 web·worker가 한 벌만 돈다는 시험이 통과한다.
- 서버 코드 버전을 바꾸면 옛 ②가 멈추고 새 ②가 뜨며, 그동안 worker가 두 벌 돌지 않고, 교체 전의 Running 런을 새 worker가 이어서 감시한다는 시험이 통과한다.
- 트레이에서 ②를 멈추고 다시 켜면 web이 응답을 멈췄다가 다시 응답한다.
- ②를 강제로 끝내면 정한 감시 방식이 ②를 다시 띄운다는 시험이 통과한다.
- 업데이트 피드에서 새 버전을 받아 앱이 다시 뜬 뒤 ②가 새 버전으로 교체되고 Running 런이 이어진다. 서명 결정 전에는 Linux나 개발용 피드로 확인한다.
- ③이 도는 기계에서 연 앱의 트레이가 ③의 상태를 보이고, 켜고 끄기를 하지 않는다.
- 패키징한 앱(개발 실행이 아닌)으로 처음 설치한 기계에서 온보딩 화면이 열린다.
