# 0.1.0 릴리스

> **보류(운영자 지시 2026-11-18).** 릴리스는 멀었다. 같은 날 운영자 결정으로 0029는 npm 패키지 대신 서버 배포물(공개하지 않음)을 만드는 일로 바뀌었고, npm 공개 여부·Changesets·0.1.0 changeset은 이 티켓으로 옮겼다. 1단계 완료 기준 시험(0030)은 저장소에서 CLI로 띄워 끝냈다(Q90). 보류를 풀 때까지 시작하지 않는다.

> **배포 경로 결정(운영자 2026-11-18).** npm으로는 내지 않는다. 0.1.0은 macOS 앱(dmg, Developer ID 서명·공증)만 GitHub Release에 올린다. Linux·macOS 서버 배포물(0029)은 이번 릴리스에 올리지 않는다. 서명 인증서는 운영자의 다른 맥북 키체인에만 있으므로, CI로 옮기지 않고 그 맥북에서 릴리스 스크립트를 돌린다. 보류는 그대로다. 공개 전에 브랜딩(Ganger, 0076~0079)을 먼저 끝낸다.

> **서명 위치 결정(운영자 2026-11-18, 위 결정의 "CI로 옮기지 않고 그 맥북에서 릴리스 스크립트를 돌린다"를 바꾼다).** 서명·공증·Release 올리기는 GitHub Actions에서 `v*` 태그를 push할 때만 돈다. PR과 `main` push에서는 돌지 않는다. 운영자의 다른 앱이 이미 같은 방식(태그 push → GitHub Actions macOS 이미지에서 서명·공증 → Release)으로 공증을 통과했다. 릴리스가 한 기계에 묶이지 않고 과정이 저장소에 남는다. 서명 맥북 점검은 끝났다(Developer ID 인증서 유효, App Store Connect API 키로 만든 notarytool 키체인 프로필로 공증 시험 Accepted). 그 프로필은 로컬 시험용으로 남긴다.

> **보류 해제(운영자 지시 2026-11-18).** 위의 보류를 푼다. 이름과 상관없는 일(서명 자리, secret, 버전·변경 기록과 자동 업데이트 결정)부터 한다. 앱 이름·번들 ID·저장소 주소가 들어가는 릴리스 스크립트와 워크플로는 0078·0079 뒤에 만든다.

## 목표

1단계를 0.1.0으로 공개한다.

## 범위

- **ADR 0005 고치기.** "npm 패키지 하나와 CLI" 배포 문장을 "macOS 앱(dmg)을 GitHub Release로 배포"로 고친다. CLI와 서비스 등록(launchd·systemd)은 그대로이고, Linux 서버 배포물은 0.1.0에 올리지 않을 뿐 지원을 접는 것이 아님을 함께 적는다. **진행(2026-11-19):** ADR 0005에 갱신 단락을 더했다.
- **릴리스 스크립트(`pnpm release:mac` 같은 이름).** 순서: 빌드 → `.app` 패키징(0046의 `@electron/packager`) → Developer ID 서명(`@electron/osx-sign`) → 공증(`notarytool`) → 공증 결과를 앱에 붙이기(`xcrun stapler staple`) → dmg 만들기(`hdiutil`) → dmg 서명·공증·staple. 서명 단계는 환경 변수가 없으면 건너뛰고 서명 없는 dmg를 만들어, 서명 없는 맥과 PR CI에서도 앞 단계를 시험할 수 있게 한다. **진행(2026-11-19):** 루트 `pnpm release:mac`(`scripts/release-mac.ts`)으로 만들었다. `APPLE_API_KEY_PATH`·`APPLE_API_KEY_ID`·`APPLE_API_ISSUER`가 모두 없으면 서명·공증을 건너뛰고, 일부만 있으면 멈춘다. 서명 identity는 키체인(`MACOS_SIGN_KEYCHAIN`, 없으면 기본 목록)에서 "Developer ID Application" 하나를 해시로 고른다. 서명은 `@electron/packager`의 `osxSign`(`@electron/osx-sign`, hardened runtime)으로 한다. 메인 앱은 JIT 하나만 주는 `apps/desktop/entitlements.mac.plist`로, Helper 앱은 osx-sign 기본 entitlements로 서명한다. 산출물은 `dist/release/Ganger-<version>-<arch>.dmg`다. 서명 없는 경로는 로컬 맥(arm64)에서 끝까지 돌려 dmg를 마운트하고 앱의 CLI가 도는 것을 확인했다.
- **dmg 설치 화면.** rc.2 dmg가 Finder 기본 창으로 열려, 끌어다 놓기 창(배경·아이콘 위치·볼륨 아이콘)을 [0094](0094-dmg-install-window.md)에서 더한다.
- **릴리스 워크플로(`.github/workflows/release.yml`).** `push: tags: ["v*"]`에서만 돈다. 태그가 `apps/desktop` 버전과 맞는지, 태그 커밋이 `origin/main`에 들어 있는지 먼저 본다. `ci.yml`에 `workflow_call`을 더해 재사용하고, 그 시험을 돌리는 동안 GitHub Actions macOS 이미지에서 임시 키체인에 인증서를 넣고 릴리스 스크립트를 돌린다. 받은 dmg를 마운트해 `codesign --verify --deep --strict`, `xcrun stapler validate`, `spctl --assess`로 확인한 뒤, 시험과 빌드가 모두 통과해야 `gh release create`로 올린다. 앱 아이콘 `.icon`을 컴파일하려면 macOS 26·Xcode 26 이상이 필요하니(0077), 그 조건을 채우는 이미지를 고른다. **진행(2026-11-19):** `release.yml`을 만들었다(plan → `ci.yml` 재사용 check와 `macos-26` 이미지(arm64, Xcode 26.6 기본)의 서명·공증·확인을 함께 → publish). 태그·버전·main 확인은 `scripts/release-plan.ts`가 한다. 서명 경로는 PR에서 돌 수 없어 actionlint로 문법만 봤고, 실제 서명은 `v0.1.0-rc.1` 태그로 시험한다.
- **`v*` 태그 보호.** environment는 ref가 `v*` 태그인지만 보고, 도는 워크플로는 태그 커밋의 것이다. 검토하지 않은 커밋에 태그를 달아 secret을 읽지 못하게, 저장소 ruleset으로 `v*` 태그 만들기·바꾸기를 관리자만 하게 묶는다(운영자 설정). **확인(2026-11-19):** ruleset "Release tags"(`refs/tags/v*` 만들기·바꾸기·지우기 제한, 관리자 우회)와 `release` environment(배포 규칙 `v*` 태그, secret 다섯 개)가 있다. 바꾸지 않았다.
- **앱 아이콘 눈 확인.** 0077이 미룬 확인이다. 0.1.0 dmg의 앱 아이콘을 macOS 26 이상과 macOS 15 이하에서 눈으로 본다. CI가 대신하지 못한다.
- **비밀 값은 저장소에 넣지 않는다.** 인증서와 키는 GitHub `release` environment의 secret으로만 둔다(ADR 0005, AGENTS.md 공개 저장소). API 키로 공증하고 서명 identity를 이름으로 찾으므로 팀 ID는 두지 않는다. environment의 배포 규칙을 `v*` 태그로 묶어, 태그 push가 아닌 워크플로는 secret을 읽지 못하게 한다. 서명 identity는 임시 키체인에서 "Developer ID Application"으로 찾으므로 인증서 이름을 따로 두지 않는다.
  - `MACOS_CERT_P12`: Developer ID Application 인증서와 개인 키를 내보낸 `.p12`의 base64
  - `MACOS_CERT_PASSWORD`: 그 `.p12`의 암호
  - `APPLE_API_KEY`: App Store Connect API 키 `.p8`의 base64
  - `APPLE_API_KEY_ID`, `APPLE_API_ISSUER`: 그 키의 Key ID와 Issuer ID
- **0.1.0 버전과 변경 기록(운영자 결정 2026-11-18).** Changesets와 `CHANGELOG.md`는 두지 않는다. 루트와 `apps/desktop`의 `package.json` 버전을 PR로 올리고 머지한 뒤 `v0.1.0` 태그를 push한다. Release 본문은 `gh release create --generate-notes`가 머지된 PR 제목으로 만든다. 태그에 `-`가 있으면(`v0.1.0-rc.1`) prerelease로 올려, 정식 태그 전에 서명·공증 경로를 시험한다. 태그가 `package.json` 버전과 맞아야 하므로 rc마다 버전을 올리는 PR이 따로 필요하다. 정식 태그의 노트가 마지막 rc 뒤의 PR만 담지 않도록 `--notes-start-tag`로 앞 정식 태그부터 모은다. **진행(2026-11-19):** rc.1 준비 PR에서 루트와 `apps/desktop`의 버전을 `0.1.0-rc.1`로 올리고, 워크플로의 모든 액션을 커밋 SHA로 고정했다. 머지 뒤 `v0.1.0-rc.1` 태그로 서명·공증 경로를 시험한다. **흐름 바꿈(운영자 결정 2026-11-19, [0087](0087-release-on-version-merge.md)).** 버전 올리기 PR은 Actions의 "Prepare release"가 열고, 그 PR이 머지되면 "Tag release"가 GitHub App 토큰으로 `v<version>` 태그를 만들어 그 tag push가 `release.yml`을 시작한다. 관리자가 태그를 손으로 push하지 않는다(손으로 push하는 길은 남긴다). release-please는 쓰지 않는다.
- 앱에 묶은 서드파티 코드의 라이선스 고지를 공개 전에 정한다(0029 「남은 위험」). **진행(2026-11-19):** #118에서 만들었다. 고른 것과 이유:
  - npm 의존성은 `pnpm licenses list --prod`가 아니라 빌드가 실제로 묶은 모듈에서 목록을 뽑는다(vite 플러그인 `thirdPartyManifest`, `scripts/third-party.ts`). `--prod`는 묶이지 않는 babel·lightningcss(MPL)를 넣고, devDependency인데 묶이는 srvx를 빠뜨린다. 패키지의 라이선스 파일 원문을 넣고, 파일이 없는 패키지는 `scripts/licenses/`의 표준 원문을 넣는다. 표준 원문이 없는 라이선스면 `pnpm run bundle`이 멈춘다.
  - 고지는 앱 화면·메뉴가 아니라 파일로 둔다. 동봉으로 고지 의무를 채우고, 화면을 더하면 메시지 파일과 Settings까지 범위가 커진다. 고지 파일은 `.app/Contents/Resources/`에 `THIRD_PARTY_LICENSES.txt`(데스크톱 main·preload·renderer), `server/THIRD_PARTY_LICENSES.txt`(web·worker·cli 서버 배포물), `LICENSE.electron.txt`(Electron), `LICENSES.chromium.html`(Chromium과 Electron이 담은 Node.js·BoringSSL·ICU·FFmpeg 등)로 들어간다. Node는 Electron 실행 파일을 `ELECTRON_RUN_AS_NODE`로 쓰므로 따로 묶지 않는다.
  - 폰트는 묶지 않는다. 글꼴 토큰이 Pretendard 같은 이름만 적고 설치된 글꼴이나 시스템 글꼴을 쓰므로 고지할 폰트 파일이 없다.
  - 만드는 과정: `pnpm run bundle`과 `apps/desktop/scripts/package.ts`(`pnpm release:mac`이 부른다)가 고지 파일을 만들고, `findBundleProblems`·`findAppProblems`(`scripts/bundle-check.ts`)가 고지가 없거나 비었으면 실패한다. 손으로 고치는 파일은 없다. copyleft 라이선스가 있으면 `bundle`이 경고를 낸다.
  - 확인: rc.4 기준으로 로컬에서 build → bundle → package를 돌려, `.app` Resources에 고지 파일 네 개가 있고 데스크톱 13개·서버 37개 패키지(MIT·Apache-2.0·BSD-3-Clause 등)가 실린 것을 봤다.
- web 서버 번들에 남는 빌드 기계의 절대 경로(TanStack Start 매니페스트 `filePath`)를 공개 전에 지운다(0029 「남은 위험」). **진행(2026-11-19):** #118에서 web 빌드에 `relativeBuildPaths`(`scripts/build-paths.ts`)를 더해 매니페스트 `filePath`를 저장소 기준 상대 경로로 바꿨다. `scripts/bundle-check.ts`의 `findBundleProblems`는 서버 배포물의 텍스트 파일에, `findAppProblems`는 `app.asar`와 앱에 묶인 서버 배포물에 저장소 루트나 홈 디렉터리(`/Users/<x>/`, `/home/<x>/`, `C:\Users\<x>\`) 절대 경로가 남으면 실패한다(`scripts/bundle-check.test.ts`, `scripts/build-paths.test.ts`). CI는 `bundle`·`smoke:bundle`로, 릴리스는 `package.ts`로 이 검사를 돈다. rc.4 기준 로컬 package 결과의 Resources 전체에서 홈 경로가 나오지 않았다. 홈 밖 절대 경로(`/opt` 등)는 저장소 루트가 아니면 검사하지 않는다.
- **자동 업데이트는 0.1.0에 넣지 않는다(운영자 결정 2026-11-18).** 0.1.0은 dmg만 올리고, 새 버전은 Release에서 다시 받는다. 업데이트 피드 주소가 저장소 이름(0079)에 달려 있어 [0083](0083-desktop-auto-update.md)으로 옮겼다.
- README에 macOS 앱 설치 안내를 영어로 더한다. **진행(2026-11-19):** README Desktop app에 설치 안내와 릴리스 만드는 법을 더했다.
- 운영자 준비(2026-11-18 끝남): 저장소에 `release` environment를 만들고 배포 규칙을 `v*` 태그로 묶은 뒤, 위 secret 다섯 개를 넣었다. `.p12` 암호가 맞는지는 첫 릴리스 워크플로의 인증서 가져오기 단계에서 확인된다. Apple 약관이 바뀌면 공증이 403으로 막히니, 릴리스 전에 developer.apple.com과 App Store Connect Business 화면의 약관 동의를 확인한다.

## 완료 조건

- GitHub Release의 0.1.0 dmg를 다른 맥에서 받아 Gatekeeper 경고 없이 열리고, 앱이 서버를 띄운다.
- GitHub에 `v0.1.0` 태그와 자동 생성한 Release 노트가 있다.

**확인(2026-11-19):** `v0.1.0` 정식 Release(arm64 dmg)를 release 워크플로가 서명·공증·확인을 모두 통과해 올렸다. 운영자가 다른 맥에서 dmg를 받아 열고 앱 아이콘까지 확인했다("31은 확인했고 잘 됐어"). 완료 조건을 채워 done으로 바꾼다.
