# 0065 남은 흔들리는 시험 두 가지

## 목표

CI `check`가 코드와 상관없이 실패하는 일을 없앤다.

## 배경

0061이 e2e 화면 준비 시간 초과와 토스트 문구 중복을 고쳤다. 그 뒤에도 두 가지가 남았다(2026-11-18).

- `apps/cli/src/start.test.ts` "한쪽이 먼저 끝나면 다른 쪽도 멈추고 이유를 알린다"가 CI에서 두 번 실패했다(PR #80, PR #91). 오류는 `StartError: stopped before web responded: worker exited with code 3`이다. 일부러 죽는 가짜 worker가 web이 응답하기 전에 끝나는 타이밍 경쟁으로 보이지만 확정하지 않았다. 다시 돌리면 통과했다.
- `demo/src/dev.test.ts:80`이 토스트를 페이지 전체에서 찾는다. UI SDK가 같은 문구를 스크린 리더 알림 영역에도 넣어서, 0061이 고친 것과 같은 중복으로 실패할 수 있다.

## 범위

- start.test의 실패를 재현해 원인을 증거로 확정하고 고친다. 시험이 확인하는 동작(한쪽이 끝나면 다른 쪽도 멈추고 이유를 알린다)은 바꾸지 않는다. 원인이 cli 코드의 경쟁이면 코드를 고친다.
- dev.test의 토스트 대기를 0061과 같이 토스트 영역 안으로 좁힌다.

## 완료 조건

- start.test를 CI와 비슷한 부하에서 반복해 모두 통과한 기록.
- 같은 head에서 CI `check`가 두 번 통과한다.

## 원인

### start.test

시험의 고정 타이머가 원인이다. cli 코드의 경쟁이 아니다.

- 가짜 worker는 자기가 뜬 뒤 300ms에 `process.exit(3)`으로 끝났다. `start`는 web이 응답할 때까지 기다리는데, 첫 요청은 web이 아직 듣기 전이라 실패하고 250ms 쉰 뒤 다시 요청한다. 그래서 web이 응답했다고 보는 때는 띄운 뒤 약 260ms이고, worker가 끝나는 300ms와의 여유가 40ms쯤뿐이다. web의 콜드 스타트가 조금만 늦어도 worker가 먼저 끝난다.
- 측정: 가짜 web을 띄워 응답할 때까지의 시간을 20번 쟀더니 한가할 때와 부하를 걸었을 때 모두 대부분 256~287ms였다.
- 재현: 가짜 web의 listen만 늦추고 시험을 각 5번 돌렸다. 0·100·200ms는 모두 통과했고, 260·300ms는 5번 모두 CI와 같은 `StartError: stopped before web responded: worker exited with code 3`으로 실패했다.
- web이 응답하기 전에 자식이 끝나면 `start`가 실패하는 것은 의도한 동작이다("web이 뜨기 전에 끝나면 실패하고 나머지를 멈춘다" 시험). 그래서 `start.ts`는 고치지 않는다.

### dev.test

티켓이 적은 줄(지금 80·88줄)은 토스트를 기다리지 않는다. 기다리는 문구는 카드 안의 `onboarding.tracker.checked`("연결을 확인했어요")와 `onboarding.runner.ready`("runner-a 러너가 준비됐어요")다. 온보딩을 끝까지 돌리며 토스트 영역과 스크린 리더 알림(`data-ui-sdk-announcer`)에 들어간 문구를 모두 기록했더니 "연결을 추가했어요", "저장했어요", "러너를 등록했어요. 확인을 요청했어요", "Workspace를 만들었어요"뿐이었고, 두 대기 문구는 페이지에서 각각 한 개만 걸렸다. 지금은 중복이 없다. 다만 알림 영역은 `main` 밖에 붙으므로 대기를 `main` 안으로 좁혀, 토스트 문구가 바뀌어도 걸리지 않게 한다. 토스트가 아니라서 토스트 영역 안으로 좁히지는 않는다.

## 고친 것

- `start.test`의 가짜 worker는 시험이 만드는 파일이 생기면 코드 3으로 끝난다. 시험은 `start`가 web 응답을 확인하고 돌아온 뒤에 그 파일을 만든다. 확인하는 동작(한쪽이 끝나면 다른 쪽도 멈추고 이유를 알린다)과 단언은 그대로다. web의 listen을 300ms·1000ms 늦춰도 5번씩 모두 통과했다.
- `dev.test`의 두 `getByText` 대기를 `main` 안에서 찾는다.

## 검증 기록

- 고치기 전: 18코어 맥에서 busy loop 54개(3배)·180개(10배)를 걸고 "한쪽이 먼저 끝나면" 시험을 20번·10번 돌렸을 때 모두 통과했다. 부하만으로는 재현하지 못해 위의 listen 지연으로 재현했다.
- 고친 뒤: busy loop 180개(코어의 10배)를 건 채 `start.test.ts` 전체(시험 13개)를 30번 돌려 30번 모두 통과했다.
- `demo/src/dev.test.ts` 2개 시험이 통과했다.
