# 0096 러너의 GitHub push 확인 바로잡기

## 목표

러너의 GitHub push 확인이 틀리게 실패하지 않게 하고, 한 저장소의 push 실패가 러너 전체를 할당에서 빼지 않게 하며, 확인 중과 결과를 한눈에 보이게 한다.

## 배경

운영자가 겪은 문제(2026-11-19).

1. **틀린 실패.** 러너에서 같은 `git push --dry-run` 명령을 직접 돌리면 exit 0인데 확인 결과는 "갖추지 못했어요"인 저장소가 있다. 키체인 문제를 고친 뒤에도 한 저장소가 남았다.
2. **모든 저장소가 통과해야 다음으로 간다.** Orca에 추가된 저장소 전부를 확인하고 하나라도 실패하면 러너를 할당에서 빼고 온보딩도 넘어가지 못한다.
3. **확인 중 표시가 없다.** 확인을 요청한 뒤 결과가 올 때까지 아무 표시가 없다.

## 원인(재현으로 확인)

러너 기계에서 Orca 프로젝트 12개에 확인 명령을 그대로 돌려 보니 포크 저장소 하나만 실패했다(`remote: Permission to <원본>.git denied`). Orca 프로젝트의 `gitRemoteIdentity.remoteName`은 프로젝트를 정하는 원본 저장소의 remote(`upstream`)를 가리키는데, 확인은 이 remote로 push해 봤다. 런이 브랜치를 올리는 곳은 git의 기본 push remote(포크인 `origin`)이고, 운영자가 직접 돌린 명령도 `origin`을 썼다.

함께 살핀 다른 가설은 원인이 아니었다.

- 비대화형 ssh 셸의 PATH·HOME: 같은 기계의 다른 11개 저장소가 같은 셸에서 통과했다.
- 여러 저장소를 동시에 확인할 때의 경합: 확인은 저장소마다 차례로 돌았고, worker의 tick은 한 번에 하나만 돈다.
- 시간 제한: 시간 초과는 `satisfied: null`(모름)로 기록돼 "갖추지 못했어요"가 되지 않는다.
- Orca 프로젝트 경로(setup.path)가 다른 클론을 가리킴: 실패한 저장소의 setup은 하나였고 그 경로의 클론이 맞았다. 다른 점은 remote뿐이었다.

## 범위

- **push 확인(`packages/runner-orca`).** push할 remote를 git처럼 고른다: `remote.pushDefault` → `origin`(있으면) → Orca 프로젝트의 remote. 실패하면 짧게 쉬고 한 번 다시 시도한다. 실패 이유를 stderr에서 한 줄 뽑아(토큰·URL의 계정 정보·경로는 가림) 인증 실패/네트워크/시간 초과/기타로 나눠 확인 결과에 담는다. 저장소 여럿은 몇 개씩 함께 확인해 기다리는 시간을 줄인다.
- **할당 조건(`packages/core`, `packages/db`, `packages/app`).** 러너가 할당에서 빠지는 조건은 러너 전체 조건만이다. push 실패는 그 러너 쪽 프로젝트에만 걸어, 그 프로젝트로 Mapping된 티켓만 그 러너에 맡기지 않는다(자동·수동 할당, 대기열 모두). 결정은 [ADR 0014](../adr/0014-push-check-per-project.md)에 남긴다.
- **worker.** 확인 요청을 주기 확인보다 먼저 처리해 요청한 확인이 바로 돌고, 같은 tick에서 같은 러너를 두 번 확인하지 않는다.
- **Runners 패널 확인 항목.** 러너 전체 항목과 GitHub push를 나눈다. push는 "12개 중 11개 통과 · 실패: 저장소(이유)"로 묶고 같은 해결 안내는 한 번만 보인다. 패널에 다시 확인 버튼을 두고, 확인 중에는 경과를 보인다. 행 문장에 push가 안 되는 저장소 수를 붙인다.
- **온보딩 러너 단계.** 러너 전체 조건(ssh, Orca 서비스, 오류 없음)이 통과하면 다음으로 간다. push 실패는 경고로 보인다. 확인 중에는 경과를 보인다. 화면 개편은 함께 도는 0095가 맡아, 이 티켓은 결과 데이터 모양과 통과 조건, 경고·경과 문장만 맞춘다.

## 완료 조건

- 시험(`packages/runner-orca`): 포크 저장소에서 `origin`으로 push 확인, `remote.pushDefault` 우선, `origin`이 없으면 프로젝트 remote. 실패 분류 넷과 이유 가림(토큰, URL 계정, 경로). 한 번 다시 시도해 통과하면 통과. 실패 결과가 프로젝트에만 걸림. 실제 git 저장소로 원인 재현(로컬 bare 저장소 둘, 쓰지 못하는 `upstream`).
- 시험(`packages/core`): push가 깨진 프로젝트의 티켓은 그 러너에 할당하지 않고 다른 프로젝트 티켓은 할당한다. 대기열에서 정한 러너의 프로젝트 push가 깨지면 러너를 비운다. 수동 할당도 막는다.
- 시험(`packages/db`, `packages/app`): 저장한 확인 결과에서 막힌 프로젝트를 읽는다. push 요약(통과 수, 실패 목록, 이유).
- 시험(worker): 확인 요청을 먼저 처리하고 같은 tick에서 두 번 확인하지 않는다.
- 화면 시험: Runners 패널의 push 요약, 실패 이유, 해결 안내 한 번, 확인 중 경과. 온보딩: push 실패여도 러너 단계 통과, 경고 문장, 확인 중 경과.
- 스크린숏: 확인 중, 일부 실패, 모두 통과(온보딩·Runners 패널).
- 마무리 리뷰: `better-interface` 리뷰 → HIGH·MEDIUM 고침 → `interface-review`로 새 서브에이전트 리뷰 → 표를 PR 본문에.
