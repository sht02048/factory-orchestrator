# 0143 CI 를 나눠 e2e 를 shard 로 동시에 돌리기

## 목표

CI `check` 가 한 잡에서 9~13분 걸리고 그 대부분이 e2e 다([research 0018](../research/0018-e2e-speed.md)). 운영자 결정(2026-11-20)으로 리서치 권장 순서의 1단계를 한다: 시험 코드를 바꾸지 않고 CI 를 잡 여럿으로 나누고, 브라우저 시험을 shard 로 동시에 돌린다.

## 할 일

- [x] `.github/workflows/ci.yml` 을 잡 여럿으로 나눈다.
  - `scope`: Markdown 만 바꿨는지 가린다(지금 규칙 그대로).
  - `static`: typecheck → lint → 색 검사 → 길이 값 검사 → format check → 단위 시험(`e2e`·`demo` 밖 project) → build → smoke:web → smoke:cli → bundle → smoke:bundle. 순서와 내용은 지금 그대로다.
  - `browser`: `e2e`·`demo` project 를 matrix shard 로 나눠 `vitest --shard` 로 돌린다. 실패 스크린숏은 shard 마다 다른 이름으로 올린다.
  - `check`: 모든 잡을 기다려(`if: always()`) 결과를 본다. 어느 잡이든 실패·취소이거나, 돌아야 했는데 건너뛰었으면 실패한다. Markdown 만 바꾼 변경이면 나머지 잡을 건너뛰고 성공한다. develop·main ruleset 의 필수 상태 검사 이름 `check` 를 그대로 둔다.
- [x] `workflow_call` 로 부르는 Release 가 그대로 동작하는지 확인한다.
- [x] shard 를 일부러 실패시켜 `check` 가 실패하는지 한 번 확인한다. 이 브랜치를 베이스로 한 검증용 PR 두 개에서 확인하고 닫아, 이 PR 에는 그 커밋이 없다.
- [x] README·AGENTS.md 의 CI 단계 설명을 바뀐 구조에 맞춘다.
- [x] 잡별·shard 별 CI 시간을 재어 shard 수와 shard 당 워커 수를 정하고 근거를 아래에 적는다.

## shard 수와 워커 수

리서치 권장(shard 4개, shard 당 `--maxWorkers=2`)을 그대로 쓴다.

2026-11-20 에 두 번 쟀다. A 는 검증용 PR #186(run 44731529017, 실패하는 시험 파일 하나를 더해 shard 가 9·8·8·8개 파일로 나뉨, 잡 이름은 `browser (1/4)` 꼴), B 는 이 PR(#188, run 44732479286, head 7da7505)이다.

- 실행 전체 3분 43초·4분 26초로, 나누기 전 9~13분에서 크게 줄었다. B 는 리서치 예상(3~4분)보다 26초 길다.
- shard 는 파일 경로 hash 순으로 개수만큼 자르므로 파일이 하나 늘거나 줄면 나뉨이 바뀐다. 실제 파일 구성인 B 에서 가장 긴 shard(222초)가 가장 짧은 shard(126초)의 1.76배로, 리서치가 시간으로 나누는 sequencer 를 쓰자고 한 기준(1.5배)을 넘는다. 이 PR 범위(1단계, 시험 설정을 바꾸지 않음) 밖이라 아래 3단계 후속으로 둔다.
- 그래도 shard 4개·워커 2를 유지한다. shard 를 늘리면 잡마다 준비 시간(체크아웃·pnpm·node·install 약 15초, pnpm 캐시를 그대로 씀)이 더 들고, hash 나뉨이 고르지 않은 문제는 그대로다. 워커를 3으로 올리면 리서치가 흔들림의 원인으로 본 부하가 다시 커진다.

## 범위 밖

리서치 권장 순서의 2~4단계는 후속 후보로 남긴다(티켓은 아직 만들지 않는다).

- 2단계: 파일당 첫 열기 시간을 나눠 잰다(`createServer`·`chromium.launch`·첫 페이지). 의존성 묶기 몫이 크면 Vite 의존성 캐시를 미리 만들어 나눠 쓴다(리서치 선택지 B).
- 3단계: hash shard 가 기울면(가장 긴 shard 가 가장 짧은 shard 의 1.5배 넘음) 시간으로 나누는 sequencer 를 쓴다. 이 PR 의 실행 B 에서 1.76배였으므로 가장 먼저 할 후보다.
- 4단계: 흔들림 티켓이 나오는 파일부터 고정 기다림·`networkidle` 을 가짜 시계·화면 신호로 바꾼다(리서치 선택지 D).

시험 코드와 앱 코드는 바꾸지 않는다. shard 별 시간은 한 실행에서만 쟀다. 리서치 「확인할 것」의 10회 이상 측정과 흔들림 횟수 비교는 머지 뒤 후속에서 한다.

## 완료 조건

- PR 의 CI 에서 `static`, `browser` shard 들, `check` 가 모두 통과한다.
- shard 하나를 일부러 실패시킨 커밋에서 `check` 가 실패한다(그 커밋은 PR 에 남기지 않는다).
- Markdown 만 바꾼 변경에서 `check` 가 성공한다.
- 화면 변경 없음. DB 변경 없음. two-way.
