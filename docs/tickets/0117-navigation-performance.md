# 0117 화면 이동 속도 재기와 개선

## 목표

레일로 Dashboard·Tickets·Runs·Runners·Stats·Settings 사이를 옮길 때 기다리는 시간을 재고, 원인별로 줄인다. 빨라진 대신 오래된 상태를 보이면 안 된다.

## 배경

운영자 보고(2026-11-19): 화면 사이를 옮길 때 너무 오래 걸린다. 미리 읽기나 캐시가 어떻게 되어 있는지 모르겠다.

## 재는 법

- `node e2e/src/measure-navigation.ts --url <웹 주소> [--repeat 3] [--client apps/web/dist/client]`: 레일 링크를 눌러 각 화면이 다 그려질 때까지(라우터가 그 경로를 읽고 쉴 때까지, 두 프레임 뒤) 시간과 그동안 부른 서버 함수를 표로 낸다. 바로 누르는 첫 방문(first), 다시 들어가기(again), 300ms 올려 두었다 누르는 첫 방문(hover)을 잰다. `--client`를 주면 클라이언트 JS 묶음 크기도 낸다.
- 프로덕션: `pnpm --filter @ganger/web build` 뒤 `pnpm dev`가 만든 시드 DB를 복사해 `DATABASE_PATH`·`ENCRYPTION_KEY`로 `apps/web`에서 `pnpm start`. 실제 어댑터라 시드의 트래커 연결이 Linear 를 부르고 가짜 키로 실패한다. 그 왕복이 실제 트래커 지연과 비슷하다.
- 개발: `pnpm dev --static`(가짜 어댑터, 외부 지연 없음).
- 로더별 SQL 수: `apps/web/src/server/loader-queries.test.ts`가 런을 늘려도 문장 수가 그대로인지 본다.

## 잰 결과(고치기 전)

프로덕션 빌드, 시드 데이터, 3번 중앙값(ms). 서버 함수 이름은 프로덕션에서 가려져 화면 이름으로 적었다.

| 경우                      | Dashboard | Tickets | Runs | Runners | Stats | Settings |
| ------------------------- | --------: | ------: | ---: | ------: | ----: | -------: |
| 첫 방문, 바로 누름        |        99 |     538 |  101 |      96 |    99 |     1436 |
| 다시 들어가기             |        60 |      67 |   68 |      66 |    65 |       68 |
| 첫 방문, 300ms 올려 둔 뒤 |        82 |     531 |   76 |      81 |    79 |     1415 |

- 서버 함수는 DB 만 읽는 화면이 10~20ms다. Tickets(약 0.5초)와 Settings(1.3~1.4초)만 느리다. 둘 다 로더가 트래커 API 를 기다린다. Settings 는 프로젝트 목록 → 상태 → 라벨을 차례로 기다려 왕복이 세 번 쌓인다.
- 미리 읽기가 없어(`defaultPreload` 없음) 포인터를 올려 두어도 빨라지지 않는다.
- 로더가 1초 안에 끝나지 않으면 라우터 기본값(`defaultPendingMs` 1초) 때문에 그동안 이전 화면이 그대로 있어 눌렸는지 알 수 없다.
- 다시 들어가기가 빠른 것은 캐시 덕이지만, Tickets·Runs·Stats 는 `shouldReload: false`라 다시 들어가도 새로 읽지 않았다. 캐시가 사라질 때(5분)까지 런 상태가 바뀌어도 그대로 보였다.
- Dashboard 로더는 런마다 기록을 따로 읽는 N+1 이었다. 런 62개에서 SQL 60개, 2262개에서 1620개(약 50ms). Runners 로더도 남은 워크트리마다 한 번씩 더 읽었다. Runs·Stats·셸은 런 수와 상관없다.
- 클라이언트 JS 는 24묶음 1160 KiB(gzip 372 KiB)다. 화면마다 10~15 KiB 묶음으로 나뉘어 있고, 큰 묶음은 처음 한 번 읽는 공용(zod 462 KiB, React·라우터 308 KiB)이라 화면 이동에는 끼지 않는다.
- 개발 서버(가짜 어댑터)는 모든 화면이 80~120ms 로 외부 지연이 없어 차이가 작다.

## 바꾼 것

- 라우터: `defaultPreload: "intent"`로 레일 링크에 포인터를 올리거나 포커스하면 그 화면의 코드와 로더를 미리 읽는다. 미리 읽은 데이터는 5초(`PRELOAD_FRESH_MS`) 동안 새것으로 쓴다.
- Tickets·Runs·Stats 의 `shouldReload: false`를 지웠다. 이 라우터 버전은 같은 화면 안에서 필터·선택처럼 검색값만 바뀔 때 다시 읽지 않고, 화면에 들어올 때만 지난 데이터를 먼저 그리고 뒤에서 새로 읽는다.
- Dashboard·Runners 로더가 런과 기록을 한 쿼리(`listRunsWithRecords`)로 읽는다.
- Settings 로더가 트래커 프로젝트 목록·상태·라벨을 차례로 기다리지 않고 한꺼번에 읽는다. 하나가 실패해도 지금처럼 그 묶음만 실패로 담는다.

## 잰 결과(고친 뒤)

| 경우                      | Dashboard | Tickets | Runs | Runners | Stats | Settings |
| ------------------------- | --------: | ------: | ---: | ------: | ----: | -------: |
| 첫 방문, 바로 누름        |        95 |     587 |  101 |      99 |   100 |      782 |
| 다시 들어가기             |        60 |      69 |   55 |      67 |    66 |       67 |
| 첫 방문, 300ms 올려 둔 뒤 |        67 |     244 |   79 |      45 |    43 |      232 |

- 포인터를 올려 둔 첫 방문은 트래커를 기다리는 시간만큼 줄었다(Tickets 531 → 244, Settings 1415 → 232). 다시 들어가기는 그대로 빠르면서 이제 뒤에서 새로 읽는다.
- Settings 서버 함수는 1.3~1.4초에서 0.7초 안팎이 되어, 바로 누른 첫 방문도 1436 → 782ms 다.
- Tickets 를 바로 누른 첫 방문(약 0.5초)은 트래커에서 티켓을 한 쪽 읽는 시간이라 이 티켓에서는 줄이지 못했다. 이 숫자는 Linear 왕복에 따라 3번 사이에도 50ms 남짓 흔들린다.
- Dashboard·Runners 로더의 SQL 수가 런 수와 상관없어졌다.

## 데이터가 오래돼 보이는 위험

- 미리 읽은 데이터는 5초까지 쓴다. 그 뒤에 누르면 다시 읽는다.
- 다시 들어간 화면은 지난 데이터를 먼저 보이고 왕복 한 번 뒤 새 데이터로 바뀐다. 고치기 전에는 최대 5분 동안 바뀌지 않았다.
- 셸(`_app`)과 루트의 `shouldReload: false`는 그대로다(셸 티켓 0113 범위).

## 후속 후보

- Tickets 로더의 트래커 티켓 목록을 서버에 짧게 담아 두고 트래커 webhook 으로 지우면, 바로 누른 첫 방문도 트래커를 기다리지 않는다. 오래된 티켓 상태를 보이지 않게 지우는 경로를 함께 설계해야 해서 따로 다룬다.
- 로더가 1초 안에 끝나지 않으면 이전 화면이 그대로 있다(`defaultPendingMs` 1초, pending 화면 없음). 눌렸다는 표시를 레일이나 셸에 두는 것은 셸 티켓 범위다.
- 첫 클라이언트 이동은 루트 `beforeLoad`가 온보딩 완료를 서버에 한 번 묻고 나서 로더를 돈다. 서버 렌더 때 이미 안 값을 넘기면 왕복이 하나 준다(루트·셸 범위).
