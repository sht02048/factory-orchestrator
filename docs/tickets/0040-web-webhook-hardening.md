# webhook 수신 보안 보강

## 목표

webhook 주소는 Funnel 등으로 밖에 열린다(스펙 8절). 0027 리뷰가 남긴 위험을 막는다. 운영자 결정(2026-11-18)으로 0029 앞에 둔다.

## 범위

- 이 티켓은 `apps/web`의 webhook 수신 코드(`src/webhooks/receive.ts`)와 라우트만 고친다.
- 본문 읽기에 시간 제한을 둔다. 시간은 조각마다가 아니라 본문 전체에 준다. 기본값은 `WEBHOOK_BODY_TIMEOUT_MS` 5초이고, 트래커가 5초 안에 200을 받지 못하면 다시 보내기 때문이다(research 0002 B.2). `WebhookContext.bodyTimeoutMs`로 바꿀 수 있다.
- 연결 ID가 있는지 드러내지 않는다. 검증을 통과하지 못한 요청(없는 연결, 서명 실패, 타임스탬프, 읽는 도중 상한을 넘은 본문, 시간 안에 오지 않은 본문)은 모두 같은 401 `unauthorized`로 답하고, 이유는 안쪽 기록에 구분해 남긴다. 선언한 Content-Length가 상한을 넘으면 연결을 찾기 전에 413으로 답해 연결이 있든 없든 같다. 400 `malformed`는 서명이 맞은 뒤에만 나온다.
- 없는 연결은 본문을 읽지 않고 끊는다(cancel).
- 연결 복호화, 어댑터 생성, DB 쓰기, 부팅 설정 오류는 기록하고 내용 없는 500 `error`로 답한다.

## 완료 조건

- 조금씩 흘려 보내거나 아무 바이트도 보내지 않는 본문(가짜 스트림)이 시간 제한에서 끊기고 401이라는 테스트가 통과한다.
- 없는 연결, 서명 실패, 오래된 타임스탬프의 응답이 상태·헤더·본문까지 같고, 기록은 이유를 구분한다는 테스트가 통과한다.
- 없는 연결이면 본문을 끊고 읽지 않는다는 테스트가 통과한다.
- 비밀값을 열지 못하거나 어댑터를 만들지 못하면 기록하고 500이라는 테스트가 통과한다.

## 남은 위험

- 응답 시간으로는 연결이 있는지 알 수 있다. 없는 연결은 본문을 읽지 않아 바로 답한다.
- 연결이 있고 서버 설정이 깨진 경우에만 500이 나온다. 운영자가 고쳐야 할 상태라 기록을 우선했다.
- 거절할 때마다 기록을 남기므로 밖에서 요청을 많이 보내면 기록이 늘어난다. 요청 수 제한은 webhook을 여는 쪽(Funnel, 리버스 프록시)에서 한다.
