# 0131 develop CI 를 빨갛게 만드는 흔들리는 시험 둘

## 목표

develop CI 를 부하에서만 실패하게 만드는 시험의 원인을 찾아 고친다. 0121 처럼 제한 시간을 늘리거나 재시도를 켜지 않고, 시험이 기다리는 조건을 바로잡는다. 원인이 제품에 있으면 제품을 고친다.

- `e2e/src/settings.test.ts` '목차를 누르면 그 구역으로 옮겨 제목에 포커스를 주고 지금 구역으로 표시한다'(0119): `expected '고급' to be 'Workspace'`
- `apps/desktop/src/renderer/notification-settings.test.ts`(0103) 첫 시험 5초 초과
- 다른 후보: desktop `local-server.test.ts` ServerWatch, settings·러너 등록 e2e 가끔 흔들림(0122·0123 보고)

## 배경

2026-11-20 develop push CI 가 두 번(1e287f6, 47d6c36) 실패했고 PR #166(0130)도 같은 이유로 실패했다. 그 파일만 돌리면 통과하고 전체를 함께 돌릴 때만 실패한다.

## 원인

### Settings 목차: 부드러운 스크롤이 끝나기 전에 휠을 굴렸다

- 목차를 누르면 `SectionNav`가 바로 그 구역을 지금 구역으로 표시하고 제목에 포커스를 둔 뒤 부드러운 스크롤(`scrollIntoView({ behavior: "smooth" })`)을 시작한다. 시험은 포커스와 표시만 보고 곧바로 `mouse.wheel(0, -5000)`을 보냈다.
- CPU 를 20배 느리게 해 스크롤 이벤트를 기록하면, 휠은 스크롤 애니메이션 중간(23ms, 위치 315/557)에 들어가 위로 움직이지 못하고 애니메이션은 끝(557, 고급)까지 간다. 목차가 고급을 보이는 것은 실제 스크롤 위치와 맞는다. 제품 버그가 아니고, 시험이 스크롤이 끝나기 전에 다음 동작을 했다.
- 같은 시험 뒷부분은 서버 구역을 누른 뒤 `waitForTimeout(800)`으로 스크롤이 끝나기를 어림해 기다렸다. 같은 경주다.
- 스크롤 도중 다른 스크롤이 끼어들면 목차가 누른 구역에 묶여 남는지도 확인했다. 첫 스크롤 이벤트 뒤 `scrollTo({ top: 0 })`로 끊어 보면 끊긴 스크롤의 `scrollend`가 고정을 풀고 뒤의 스크롤 이벤트가 다시 판단해 Workspace 로 돌아온다. 제품은 고치지 않았다.

### Settings MCP 스위치: 저장했다고 알린 뒤 옛 값으로 돌아갔다(제품 버그)

- 부하에서 settings 파일 전체를 돌리면 '바로 저장하는 스위치는 저장하지 못하면 원래 값으로 되돌리고 이유를 보인다'가 `expected 'false' to be 'true'`로 실패했다(6개 동시 실행 12회 중 2회).
- `useAutoSave`는 저장이 끝나면 고른 값(`pending`)을 지우고 화면 데이터(`saved`)를 보인다. 저장 함수는 `useReloadOnSuccess`가 감싸 `router.invalidate()`를 기다리는데, TanStack Router 는 이미 읽은 화면을 `sync` 없이 무효화하면 로더를 뒤에서 돌리고 바로 끝낸다(`router-core` `load-client.ts`의 `background`). 그래서 "저장했어요"가 뜬 순간 스위치는 옛 값이고, 새 값을 다 읽은 뒤에야 다시 켜진다. 사람에게도 스위치가 잠깐 꺼졌다 켜지는 깜빡임으로 보인다.
- 0122 의 "Linear에서 다시 읽기"는 같은 이유로 `invalidate({ sync: true })`를 쓴다.

### 데스크톱 알림 설정 창: 첫 시험이 개발 서버 첫 변환 시간을 떠안았다

- `beforeAll`은 Vite 개발 서버를 띄우기만 하고, 첫 시험의 `page.goto`가 렌더러 모듈 전체(React, StyleX, `@ganger/ui`)를 처음 변환했다. 부하에서는 이것만으로 5초를 넘는다. 실패는 늘 파일의 첫 시험이었다(16개 동시 실행·CPU 부하 16회 중 8회, 모두 첫 시험).
- `e2e/src/settings.test.ts`처럼 `beforeAll`(제한 120초)에서 한 번 페이지를 열어 네트워크가 쉴 때까지 기다리면 각 시험은 시험할 동작만 잰다.
- 같은 구조인 `apps/desktop/src/renderer/screens.test.ts`는 같은 조건 16회에서 실패하지 않아 고치지 않았다.

### demo 온보딩 모드: 다음 단계가 그려지기 전에 가짜 값을 채웠다

- 코디네이터가 보탠 후보다. PR #166 CI(d931ce3)에서 `demo/src/dev.test.ts` '온보딩 모드: 가짜 값으로 5단계를 마치면 홈이 열린다'가 4단계 '만들기'가 꺼진 채로 30초를 넘겼다.
- 시험은 "다음"을 누르자마자 "가짜 값 채우기"를 누른다. 단계를 옮기는 것은 라우터 이동이라 새 단계 폼은 화면을 다 읽은 뒤에 그려진다. 그 전에 채우기를 누르면 채울 칸이 없고(`prefill.ts`는 그 순간의 `main input[name]`만 채운다) Workspace 이름이 빈 채로 남아 '만들기'가 켜지지 않는다. 3단계의 "직접 입력" 링크 뒤 채우기도 같은 경주다.
- 화면 읽기(GET 서버 함수)를 1초 늦추면 고치기 전 시험이 3회 모두 같은 자리('만들기' 비활성)에서 실패한다.
- 5단계에서는 앞 선택을 저장하고 다시 읽는 동안 다음 칸을 열었다. 이 티켓의 `invalidate({ sync: true })`로 저장 중인 시간이 다시 읽기까지 늘어, 부하에서 30회 중 1회 'factory' 선택지가 자리를 잡지 못해 누르지 못했다. 사람은 앞 선택이 저장된 것을 보고 다음 칸을 고른다.
- 실패 스크린숏은 `finally`가 페이지를 닫은 뒤 `onTestFailed`가 찍으려 해 늘 "Target page … has been closed"로 실패했다.

### /ds 탭 e2e

- 코디네이터가 보탠 후보다(0130 전체 e2e 한 번 실패, 단독 통과). 실패 로그가 없고, `e2e/src/ds.test.ts`를 8개 동시 실행 16회 돌려 모두 통과해 재현하지 못했다. 고치지 않았다. 다시 실패하면 실패 메시지와 `e2e/test-results`의 스크린숏으로 어느 기다림에서 멈췄는지부터 본다.

### 함께 본 다른 후보

- ServerWatch(`local-server.test.ts`): CPU 부하와 8개 동시 실행 16회에서 실패하지 않았다. 실제 노드 프로세스를 띄우고 죽이는 시험이라 원인이 다르다(0121 에서도 따로 남김). 재현하지 못해 고치지 않았다. 다시 실패하면 실패 로그의 어느 단계(`ensureRunning` 준비 대기, `tick`의 재기동)에서 시간이 걸렸는지부터 본다.
- 러너 등록 e2e(`runner-setup.test.ts`): 6개 동시+CPU 부하 12회 중 1회 '직접 입력에서 orca 경로를 비우면 ssh로 찾고, 닿지 않으면 …'이 30초 안에 경고를 보이지 못해 실패했다. 이 시험은 실제 `ssh`로 `nowhere.invalid`에 닿지 못하기를 기다린다. 이름 풀이와 ssh 프로세스가 부하에 밀리는 것이라 원인이 다르다. 고치지 않았고 다음 티켓 후보로 남긴다(가짜 ssh 로 바꾸는 방향).
- 같은 실행에서 Vite 가 hydration 불일치를 알렸다. 러너 확인 줄의 "확인하는 중이에요 · 9초째"를 서버와 브라우저가 다른 시각으로 그려 10초째와 어긋났다. 시험 실패의 원인은 아니고, React 가 그 트리를 다시 그린다. 이 티켓 범위 밖이라 남긴다.

## 고친 것

- `e2e/src/settings.test.ts` 목차 시험: 휠을 굴리기 전과 `scrollTo` 전에 `scrollSettledAt(id)`(두 프레임 동안 스크롤 위치가 그대로이고, 그 구역이 `scroll-margin-top` 자리에 있거나 더 내려갈 수 없는 끝)를 기다린다. `waitForTimeout(800)`을 뺐다.
- `apps/web/src/settings/use-settings-actions.ts`: 저장 뒤 다시 읽기를 `router.invalidate({ sync: true })`로 기다린다(`useReloadOnSuccess`, `createLabel`). 저장 결과를 알릴 때 화면은 이미 새 값이다.
- 새 e2e '바로 저장하는 스위치는 화면이 새 값을 늦게 읽어도 저장했다고 알릴 때 이미 새 값을 보인다': 화면 읽기(GET 서버 함수)를 500ms 늦추고 저장 직후 스위치 값을 본다. 고치기 전 코드에서 실패하고 고친 뒤 통과한다.
- `apps/desktop/src/renderer/notification-settings.test.ts`: `beforeAll`에서 렌더러를 한 번 열어 네트워크가 쉴 때까지 기다린다.
- `demo/src/dev.test.ts`: "다음"을 누른 뒤 새 단계 제목이 보일 때까지, "직접 입력"을 누른 뒤 ssh 대상 칸이 생길 때까지 기다리고 채운다. 5단계에서는 고른 뒤 목록·메뉴가 닫히고 "저장하는 중…"이 없어질 때까지 기다린다. 실패 스크린숏은 페이지를 닫기 전에 `catch`에서 찍는다.
