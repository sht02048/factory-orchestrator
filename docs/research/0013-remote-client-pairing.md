# 원격 서버와 데스크톱 클라이언트 연결 (발견·페어링·릴레이)

조사일 2026-11-18. 운영자는 상시 기계에서 서버(③ 헤드리스 서비스 또는 ① 앱 + ② 서버)를 띄우고, 실제로는 다른 기기(노트북, 휴대폰)에서 클라이언트로 쓴다. 노트북에서도 앱 형태로 보고 싶어 한다. 이 문서는 클라이언트가 서버를 어떻게 찾고 붙을지, 온보딩에서 tailnet을 쓰게 할지, 릴레이를 쓸 수 있는지를 레퍼런스 제품과 비교해 정리한다. 제품 코드는 바꾸지 않았다. 결정은 운영자 몫이라 ADR은 쓰지 않고 권장안과 남은 결정만 적는다. 같은 날 정한 0046 그릴링 결정(Q1~Q8)은 티켓 [0046](../tickets/0046-desktop-app.md)에 적었다.

①·②·③은 research [0012](0012-desktop-app-packaging.md)와 같은 뜻이다. ① Electron 앱(창·트레이·알림), ② 앱에서 분리된 서버(`start`가 띄우는 web + worker), ③ 헤드리스 서비스(`service install`).

출처 표시는 research 0004·0009·0012를 따른다.

- **[문서]** 공식 문서, 공식 저장소의 이슈·PR. 링크를 문장 옆에 단다. 2026-11-18에 찾았다. 2차 자료(블로그, 커뮤니티 글)는 그렇다고 적는다.
- **[실행]** 오케스트레이터 기계(macOS, Orca 1.4.253, Tailscale 1.104.4)에서 직접 돌린 결과. 출력의 주소·호스트명·계정은 옮겨 적지 않고 구조(필드 이름, 종류)만 적는다.
- **[추정]** 문서나 실행으로 확인하지 않은 판단. 그렇다고 적는다.

## 1. 레퍼런스 비교

### Orca (가장 중요한 레퍼런스)

운영자가 이미 쓰는 도구다. 이 기계의 `orca serve --help`, `orca environment --help`, `orca environment list --json`과 공식 문서([Remote Orca Servers](https://www.onorca.dev/docs/remote-servers))로 확인했다.

- **서버 쪽.** `orca serve`는 창 없는 런타임을 띄운다. `--bind`는 듣는 인터페이스(`127.0.0.1`, Tailscale 주소, `0.0.0.0`), `--pairing-address`는 클라이언트에 알리는 주소만 바꾼다("reachable LAN, Tailscale, SSH-forward, or reverse-proxy endpoint"). 둘이 나뉘어 있어, 서버가 듣는 주소와 클라이언트가 붙을 주소가 달라도 된다 **[실행: help]**.
- **페어링 링크.** 시작하면 페어링 링크(`orca://pair?code=...`)를 찍고, web 클라이언트 번들이 있으면 페어링 데이터를 담은 브라우저 URL도 찍는다. `--mobile-pairing`은 모바일 범위의 QR/링크를 찍고, `--no-pairing`은 끈다 **[실행: help]**. 데스크톱 클라이언트는 Settings → Remote Orca Servers → Add Server에 링크를 붙이고, 휴대폰은 같은 tailnet에서 Orca Mobile의 Pair로 QR을 읽는다 **[문서]**. App Store 소개는 "데스크톱이 일회용 키쌍을 만들어 QR로 보이고, 페어링은 종단 간 암호화된다"고 적는다 **[문서: App Store 설명]**. 코드 안의 형식은 공식 문서에 없다.
- **저장한 서버.** `orca environment add --name <이름> --pairing-code <코드>`로 저장하고, 이후 `--environment <이름>`이나 `ORCA_ENVIRONMENT`로 고른다 **[실행: help]**. 저장한 항목은 `endpoints[]`(종류 `websocket`, `ws://` 주소)와 `preferredEndpointId`, `pairedDeviceId`, `pairingRevision`, `connectionDependency`(값의 예: `ssh-tunnel`)를 갖는다 **[실행: list --json의 필드 구조]**. 곧 한 서버에 주소를 여러 개 두고 그중 하나를 고르며, 페어링한 기기 ID로 서버가 클라이언트를 알아본다.
- **서비스 모드.** 서비스(`--supervise`)는 로그에 페어링 링크를 찍지 않으므로, 데스크톱 앱에서 페어링하거나 서비스를 멈추고 터미널에서 `orca serve`를 돌려 페어링한다 **[문서]**. 같은 프로필에 다른 Orca가 이미 서빙하면 아무것도 띄우지 않고 코드 3으로 끝난다 **[실행: help]**.
- **발견과 릴레이.** 자동 발견은 없다. 클라이언트는 페어링 링크 안의 주소로 붙고, 그 주소가 닿게 하는 것(tailnet, ssh 포워드, 리버스 프록시)은 사용자 몫이다 **[실행: help][문서]**. "Relay를 쓰려면 로그인이 필요하다"는 2차 자료가 있으나 공식 문서로 확인하지 못했다 **[추정]**.

우리와 다른 점: Orca 페어링은 **접속 권한(키)** 을 함께 넘긴다. 우리는 로그인이 없으므로(Q3) 코드에 담을 비밀이 없고, 담을 수 있는 것은 주소뿐이다(2절 (d)).

### "buzz" — 확인 필요

운영자가 말한 "buzz"는 Block이 만든 오픈소스 셀프호스팅 워크스페이스 **Buzz**([`block/buzz`](https://github.com/block/buzz))로 본다 **[추정]**. 셀프호스팅 서버 + 원격 클라이언트 + 페어링이라는 질문의 모양과 맞는 후보가 이것뿐이었다. 알려진 동작은 아래와 같다.

- 서버는 `buzz-relay`(Nostr 릴레이)이고, 데스크톱·모바일·CLI 클라이언트가 `BUZZ_RELAY_URL`(공개 접속은 `wss://`)로 붙는다 **[문서: 2차 설치 안내]**.
- 데스크톱 앱 Settings → Mobile이 QR을 보이고, 모바일이 읽는다. 이 페어링은 별도 프로세스 `buzz-pair-relay`가 중계하고, 메인 릴레이가 `BUZZ_PAIRING_RELAY_URL`로 그 주소를 알린다. 페어링 릴레이는 메시지를 저장하지 않는 일회성 중계다 **[문서: PR [#4082](https://github.com/block/buzz/pull/4082), [#3627](https://github.com/block/buzz/pull/3627)]**.
- 셀프호스팅 묶음이 페어링 릴레이를 띄우지 않아 모바일이 404를 받은 이슈가 있었고, VPN 안에서만 닿는 릴레이는 모바일 앱이 "HTTPS여야 한다"·사설 주소 검사로 거절했다는 이슈가 있다 **[문서: issue [#4198](https://github.com/block/buzz/issues/4198)]**. tailnet 전용 서버를 휴대폰에서 붙일 때 HTTPS가 걸림돌이 되는 예다.

다른 후보: "buzz"가 다른 제품(예: 운영자 주변의 사내 도구)이면 위 내용은 맞지 않는다. 운영자에게 확인한다.

공통 관찰 **[추정: 위 표에서]**:

- 모든 제품이 **주소 직접 입력**을 마지막 대체 수단으로 둔다. 발견(mDNS·UDP)은 같은 LAN에서만 돌고, Docker·VLAN·VPN에서 쉽게 깨진다.
- **페어링 코드/QR**은 서버 쪽에 인증(키·계정·PIN)이 있을 때 값을 낸다. 주소만 넘기는 코드는 "주소 복사"를 편하게 할 뿐이다.
- **릴레이**는 회사가 운영하면 계정과 비용이 따르고, 사용자가 띄우면 공개 주소·TLS·토큰 관리가 따른다. 어느 쪽이든 로그인이 없는 서버 앞에 두면 릴레이 주소를 아는 누구나 서버에 닿는다.

## 2. 우리 제품의 선택지

전제: 로그인이 없다(Q3). tailnet 안의 기기를 믿고, tailnet을 함께 쓰는 사람은 Tailscale ACL로 막는다. 서버의 web은 지금 `WEB_HOST` 기본값 `127.0.0.1`로 듣는다(`apps/cli/src/init.ts`). 다른 기기에서 붙으려면 `init --host`로 바인드 주소를 바꾸거나(Tailscale 주소, `0.0.0.0`) Tailscale Serve처럼 같은 기계의 프록시가 `127.0.0.1`로 넘겨야 한다 **[실행: 코드][문서: Serve]**. web에는 Host·Origin 검사가 없다 **[실행: `apps/web/src`에서 찾지 못했다]**.

| 선택지                           | 하는 일                                                                                           | 구현 비용                                                                                                                                                                                                                                                                                                                                                                   | 보안(Q3 로그인 없음과의 관계)                                                                                                                                                               | ADR 0005                                                                                                                                                                            |

### 온보딩에서 tailnet에 연결하게 해야 하나

하지 않는다. ADR 0005는 Tailscale을 필수가 아닌 권장 구성으로 둔다. 앱이 tailnet 가입을 대신하면(b′) Tailscale이 사실상 필수가 되고, 이미 Tailscale을 쓰는 운영자에게는 같은 기기에 tailnet 노드가 둘 생긴다 **[추정]**. (b)는 이미 기기에 깔린 Tailscale을 읽기만 하므로 이 문제가 없다. Tailscale이 없으면 (a)로 넘어간다.

### 오케스트레이터가 도는 기기만 거르기

기기 목록에는 휴대폰·다른 노트북이 섞인다. 우리 서버가 도는 기기만 보이려면 기기마다 물어봐야 한다.

- **신원 확인 경로가 지금 없다 [실행].** web 라우트는 화면 라우트와 webhook 수신(`apps/web/src/routes/api/webhooks/tracker/$connectionId.ts`)뿐이고 health·version 경로가 없다. 새로 만들어야 한다. 예: `GET /api/health` → `{ "product": "factory-orchestrator", "version": "0.1.0", "instanceId": "<설치마다 만든 임의 ID>" }`. 이름과 모양은 0046에서 정한다.
  - `product`로 우리 서버인지 가린다. 다른 서비스가 같은 포트에 있어도 틀리게 붙지 않는다.
  - `version`으로 앱과 서버의 버전 차이를 알린다(0046의 "③의 버전이 다르면 알리기만 한다"와 같은 정보).
  - `instanceId`로 같은 서버를 주소가 여러 개(MagicDNS 이름, Tailscale IP, Serve HTTPS)여도 하나로 묶는다. Orca가 저장한 서버에 `pairedDeviceId`를, RPC 응답 `_meta`에 `runtimeId`를 두는 것과 같은 쓰임이다 **[실행: 필드 구조][문서: research 0003]**. 호스트명·경로·계정 같은 개인 값은 담지 않는다(ADR 0005).
  - 로그인이 없으니(Q3) 이 경로도 인증 없이 열린다. tailnet 안에서 "여기 우리 서버가 있다"와 버전을 알리는 것 외에 더 드러내지 않는다.
- **무엇을 물을지 [추정].** 후보는 `Online`이 참이고 `OS`가 휴대폰(`iOS`, `android`)이 아닌 기기다. 서버는 macOS·Linux에서만 돈다(ADR 0005). 기기마다 아래 주소를 동시에 물어, 처음 맞는 응답을 쓴다.
  `DNSName`은 끝에 점이 붙은 FQDN이다(`server.example.ts.net.`) **[실행]**. URL에 넣기 전에 끝의 점을 뗀다. 그대로 쓰면 TLS 이름 검사가 어긋날 수 있다 **[추정]**.
  1. `https://<DNSName>/api/health` — Tailscale Serve로 연 권장 구성(3절).
  2. `http://<DNSName>:<포트>/api/health` — 바인드를 Tailscale 주소·`0.0.0.0`으로 바꾼 구성. 포트는 기본값 3000(`init`의 기본값).
- **시간 제한.** 기기마다 1~2초, 모두 동시에 묻는다. tailnet 기기가 수십 대여도 화면은 2초 안에 목록을 그린다. 늦게 온 응답은 목록에 더한다 **[추정]**. 앱의 main 프로세스(Node)가 물으므로 브라우저의 CORS·혼합 콘텐츠 제한을 받지 않는다 **[추정]**.
- **포트가 기본값이 아닐 때.** 목록 화면에 "다른 포트로 찾기"를 두어 포트를 넣고 다시 찾는다. 그래도 못 찾으면 (a)로 전체 주소를 넣는다. 모든 포트를 훑지는 않는다(포트 스캔처럼 보이고 느리다).
- **ACL.** Tailscale ACL로 그 기기에 닿지 못하면 `Online`이어도 응답이 없다. 목록에 나오지 않는 것이 맞는 동작이다.
- **휴대폰.** 휴대폰은 앱이 아니라 브라우저로 붙으므로 (b)가 없다. 서버의 Settings가 보이는 주소(4절 2번)를 쓴다.

### 저장과 다음 실행

- 고른 서버의 `instanceId`, 이름(목록에 보인 기기 이름), 붙은 주소를 앱 설정에 저장한다. 다음 실행에서는 묻지 않고 그 주소로 바로 연다.
- 저장한 주소가 응답하지 않으면 같은 `instanceId`를 tailnet에서 다시 찾아본다(주소가 바뀐 경우). 그래도 없으면 "서버에 닿지 않아요" 화면을 보인다(아래 흐름).

## 3. webhook 공개 주소와의 관계

Linear webhook은 공개 인터넷에서 서버에 닿아야 한다. 지금은 시험 때 `cloudflared tunnel --url`로 임시 주소를 열었다(research [0011](0011-acceptance-run.md)). 수신 경로는 `/api/webhooks/tracker/$connectionId`다(`apps/web/src/routes/api/webhooks/tracker/$connectionId.ts`). 클라이언트 연결과 webhook은 같은 서버의 서로 다른 경로를 서로 다른 범위에 여는 문제다.

| 무엇                   | 누가 닿아야 하나    | 인증                                  | 권장 노출                                                          |
| ---------------------- | ------------------- | ------------------------------------- | ------------------------------------------------------------------ |
| 화면과 server function | 운영자의 기기만     | 없음(Q3). 망이 막는다                 | tailnet 안. Tailscale Serve(HTTPS) 또는 Tailscale 주소 바인드      |
| webhook 경로           | 트래커(공개 인터넷) | 서명 검증(ticket 0040, research 0005) | 그 경로만 공개. Tailscale Funnel, Cloudflare Tunnel, 리버스 프록시 |

- **Tailscale 하나로 둘 다 할 수 있다 [문서][추정].** Serve는 tailnet 안에서만 닿고, 자동 HTTPS 인증서로 기기의 MagicDNS 이름에 연다 **[문서]**([serve](https://tailscale.com/docs/reference/tailscale-cli/serve), [HTTPS](https://tailscale.com/docs/how-to/set-up-https-certificates)). Funnel은 같은 서빙 설정을 공개 인터넷에 열되 443·8443·10000 포트만 쓴다 **[문서]**([Funnel](https://tailscale.com/docs/features/tailscale-funnel)). 그래서 화면은 Serve로 443에, webhook 경로만 Funnel로 8443에 여는 조합이 된다고 본다 **[추정: 이 조합을 돌려 보지 않았다]**. 이때 서버는 `127.0.0.1`에 그대로 두어도 된다(Serve·Funnel이 같은 기계에서 넘긴다).
- **화면 전체를 Funnel로 열면 안 된다.** 로그인이 없어(Q3) 주소를 아는 누구나 러너에 명령하고 토큰 설정을 바꾼다. README의 경고 단락에 함께 적었다.
- **HTTPS 인증서는 기기 이름을 공개 로그에 싣는다.** Tailscale HTTPS를 켜면 기기 이름이 인증서 투명성 로그에 올라간다 **[문서]**. 기기 이름에 실명을 넣지 말라고 안내해야 한다. ADR 0005와 같은 결의 경고다.
- **온보딩이 보이는 webhook 주소가 클라이언트 주소에 따라 바뀐다.** 온보딩은 webhook 주소를 `window.location.origin` + 경로로 보인다(`apps/web/src/onboarding/onboarding-screen.tsx`) **[실행: 코드]**. Serve 주소로 연 화면은 tailnet 주소를, 노트북의 `127.0.0.1`로 연 화면은 로컬 주소를 보인다. 둘 다 트래커가 닿을 수 없는 주소다. 공개 주소(Funnel 등)를 설정으로 받아 그것을 보이는 편이 맞다 **[추정]**. 이 조사의 범위 밖이라 후속 후보로만 적는다.
- **Funnel 없이 Cloudflare Tunnel·리버스 프록시를 고른 운영자**도 화면은 tailnet(또는 LAN)으로, webhook 경로만 공개로 나누는 원칙은 같다.

## 4. 권장안

처음 권장안은 (a)만이었다. 운영자가 UX를 이유로 (a)+(b)를 정해(2026-11-18) 아래로 바꿨다.

1. **원격 모드는 (b) 찾은 서버 목록 → 못 찾으면 (a) 주소 입력이다.** 앱이 로컬 Tailscale CLI로 기기 목록을 읽고, 신원 확인 경로로 우리 서버만 보인다(2.1절). 한 번 클릭으로 붙는다. Tailscale이 없거나 꺼졌거나 서버를 못 찾으면 주소를 넣는다. 어느 쪽이든 앱이 그 주소가 우리 서버인지 확인한 뒤 저장한다.
2. **서버에 신원 확인 경로를 더한다.** 제품 이름·버전·설치 ID만 주는 인증 없는 경로(예: `/api/health`). (b)의 거르기, (a)의 연결 확인, 버전 차이 알림이 모두 쓴다. 지금 없으므로 0046(또는 그 앞 티켓)이 만든다.
3. **서버 쪽은 "다른 기기에서 열 주소"를 보여 준다.** Settings(또는 트레이)에 이 서버를 다른 기기에서 열 주소와 복사 버튼을 둔다. 휴대폰과 (b)가 안 되는 경우가 쓴다. 주소는 서버가 추측하지 않고 설정으로 받는다(예: `PUBLIC_WEB_URL`. 이름은 정해야 한다). 3절의 webhook 공개 주소도 같은 방식으로 받는다.
4. **권장 구성은 Tailscale Serve의 MagicDNS HTTPS 주소다.** 바인드를 `0.0.0.0`으로 바꾸지 않아도 되고, HTTPS라 휴대폰의 설치형 웹앱(research 0012 (C))과 Buzz 사례의 "HTTPS여야 한다" 문제도 피한다. (b)도 이 주소를 먼저 묻는다. README Self-hosting에 Serve로 화면, Funnel로 webhook 경로만 여는 예시를 둔다(0046 README 범위).
5. **(d) 페어링 코드/QR은 후속.** 지금은 주소만 담아 (a)와 차이가 작다. 휴대폰에서 긴 주소를 치기 불편하다는 요구가 생기면, 3번의 주소를 QR로 보이는 것부터 더한다. 로그인·기기 토큰을 더하게 되면 Orca처럼 키를 담는 페어링으로 키운다.
6. **(c) mDNS는 하지 않는다(후속 후보).** 다른 망에서 쓸모가 없고 로그인 없는 서버를 LAN에 알린다. 컨트롤 서버 API와 tsnet(b′)도 하지 않는다(추가 로그인).
7. **(e) 릴레이는 하지 않는다.** 우리가 운영하면 ADR 0005와 부딪히고, 사용자가 띄우는 릴레이는 Tailscale·Cloudflare Tunnel이 이미 하는 일이다.

### 운영자가 정할 것

- 원격 모드 연결 방법은 (a)+(b)로 정했다(2026-11-18). (d) QR을 처음부터 더할지.
- 신원 확인 경로의 이름과 응답 모양, 그리고 그것을 0046 안에서 만들지 앞 티켓으로 뺄지.
- (b)가 물을 기본 주소(Serve HTTPS 443과 `http://…:3000`)와 시간 제한.
- "다른 기기에서 열 주소"와 webhook 공개 주소를 설정으로 받을지, 그 설정 이름. 서버 쪽 변경이라 0046이 아닌 별도 티켓이 맞을 수 있다.
- 원격 모드의 알림(Q4)을 앱이 어떻게 받을지. 앱이 서버의 상태를 폴링할지, 서버가 알림용 스트림을 열지 0046에서 정한다(서버 API가 필요하다).
- "buzz"가 Block의 Buzz가 맞는지.

## 남은 위험

- Serve(443) + Funnel(8443, 경로만) 조합은 문서로만 확인했고 돌려 보지 않았다. Tailscale 1.52에서 serve·funnel 명령이 바뀌었으므로 README 예시는 쓰기 전에 현재 CLI로 확인한다 **[문서]**.
- web에 Host·Origin 검사가 없다. 로그인이 없는 서버가 `127.0.0.1`·tailnet 주소로 열려 있으면, 운영자 브라우저가 연 다른 사이트가 DNS 리바인딩이나 교차 출처 요청으로 server function을 부를 수 있는지 따로 확인해야 한다 **[추정: 시험하지 않았다]**. Q3(로그인 없음)의 범위 안에서 남는 위험이다.
- `tailscale status --json`의 출력은 공식 안정 계약으로 적힌 곳을 찾지 못했다. 필드가 바뀌면 (b)가 깨지므로 zod로 필요한 필드만 파싱하고 실패하면 (a)로 넘어가게 한다. Linux와 macOS 독립형·오픈소스 빌드에서는 돌려 보지 않았다(이 기계는 App Store판으로 보이는 번들 안 CLI만 있다).
- (b)는 tailnet의 Online 기기마다 HTTP 요청을 보낸다. ACL로 막힌 기기는 시간 제한까지 기다리므로 tailnet이 크면 목록이 늦게 찰 수 있다. 신원 확인 경로는 인증 없이 제품과 버전을 tailnet 안에 알린다.
- Orca 페어링 코드의 형식과 Orca Relay의 동작은 공식 문서에서 확인하지 못했다. 위 Orca 절은 CLI 도움말과 저장한 서버의 필드 구조에서 온 것이다.
- Buzz 관련 내용은 공식 저장소의 PR·이슈와 2차 설치 안내에서 왔고, 앱을 설치해 보지 않았다.
- Plex·VS Code Tunnels·Jellyfin·Moonlight는 2차 자료이거나 이번에 공식 문서를 찾지 못한 것이 섞여 있다. 결론(주소 입력이 공통 대체 수단, 발견은 같은 LAN에서만)에는 영향이 작다.
